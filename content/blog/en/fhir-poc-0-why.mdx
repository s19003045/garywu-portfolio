## The journey of one glucose value

Before becoming a software engineer, I spent 14 years as a medical technologist in a hospital laboratory.

A patient gets blood drawn. The analyzer reports glucose at 135 mg/dL. That number travels: instrument → LIS (lab information system) → technologist review and sign-off → HIS (hospital information system) → the physician's screen. Within one hospital, the pipeline works.

But when the same patient visits another hospital next week and that physician wants to see the value, everything breaks:

- The two hospitals run HIS built by different vendors, in different decades, in different languages
- Our record is coded `GLU-AC`; theirs is `009002` — each hospital's private dialect
- Even if the file gets through, the receiving system has no idea what `GLU-AC` means, whether the units match, or what the reference range was

So the patient gets their blood drawn again. Time, money, and a patient's arm — all paying for systems that can't talk.

I watched this for 14 years. After switching careers into engineering, I realized I was now standing exactly where the problem could be fixed. Hence this POC, and this series.

## The problem has two layers

Healthcare data exchange is hard because it's two problems stacked:

1. **Syntactic interoperability** — can you parse the data at all?
2. **Semantic interoperability** — does "glucose" mean the same thing on both sides?

Data that arrives but can't be understood is the same failure as data that never arrives.

**FHIR** (Fast Healthcare Interoperability Resources, pronounced "fire") is the HL7 standard, mainstream since 2014, that addresses both layers: Resources + RESTful APIs for syntax, terminology systems + Profiles for semantics. On top of it, Taiwan's Ministry of Health and Welfare publishes the **TW Core IG** (Implementation Guide), with version 1.0.0 released in late 2025 — rapidly becoming the entry ticket for data exchange between Taiwanese healthcare institutions.

## What this POC proves

Five stages, one complete chain:

```
Simulated HIS (SQLite, deliberately preserving real Taiwanese HIS quirks:
               ROC-calendar dates, in-house codes)
   ↓  TypeScript ETL (terminology mapping, data cleansing, restructuring)
FHIR Server (HAPI in Docker, TW Core IG 1.0.0 auto-installed)
   ↓  standard Search API
React viewer (patient search, lab reports, vital signs, medications)
```

Verifiable results: 608 FHIR resources uploaded, **12 TW Core profiles machine-validated with 0 errors**, and an ETL that can be re-run without creating duplicates. "Conformant to Taiwan's spec" here is not a slide-deck claim — it's a verdict returned by the `$validate` API.

Every real pitfall we hit — department codes that must be translated to SNOMED, institution codes you can't even fake, a silent SQLite sequence bug — is preserved in the articles. **The stumbles teach more than the successes.**

## One sentence before we start

Beyond technical feasibility, this series argues one thing: **the scarcest resource in healthcare IT is not tooling — it's people who speak both clinical and engineering.** An engineer can't tell `GLU-AC` from `GLU-PC`; a medical technologist can't build an ETL pipeline. Those two competencies can live in one person.
