If this is your first time opening the series, I strongly recommend starting here.

The next seven articles try to explain both the Go concepts and the learning interaction clearly, but they all assume you already know what problem this project is solving, which stage you are looking at, and which files are worth opening beside the article.

Without that background, a lot of terms can feel abrupt: WebRTC, signaling, join, signal, leave, Hub, readPump. At that point, the problem is often not that Go is hard. It is that you do not yet have a usable map.

This article is that map.

## What this project is doing

This repository is called [webrtc-poc](https://github.com/s19003045/webrtc-poc).

It is not a single demo with one fixed architecture. It is a staged WebRTC proof of concept that gradually evolves from the smallest possible 1:1 call into multi-user rooms, a React client, a Go backend, an SFU, and eventually multi-node routing and observability.

So the value of the repository is not just that it can demonstrate a working call. Its real value is that each architecture transition is isolated into a phase that can be understood on its own.

If you are still new to WebRTC, keep one thing in mind first:

WebRTC lets browsers establish real-time media or data connections, but before those peer connections succeed, both sides still need to exchange negotiation information. That exchange layer is signaling.

## What the signaling server is responsible for here

This series focuses on **Phase 4**, where the original Node signaling server is rewritten in Go.

This server does not directly process media encoding, and it is not yet an SFU. Its responsibility is closer to room coordination and message routing:

- who joins a room
- who is already in the room
- which peer a signal message should be forwarded to
- how other peers are notified when someone leaves

That is why you keep seeing `join`, `signal`, and `leave` throughout the series. They are not arbitrary labels. They describe the core events of this system.

If you think of this server as the middle layer that helps browsers find each other and exchange the information needed to establish connections, the later code becomes much easier to follow.

## Why the repository is split into phases

The phase structure matters because it tells you what kind of system this Go code grew out of.

At a high level, it looks like this:

```text
phase-1   1:1 P2P, Node + vanilla frontend
phase-2   multi-user mesh, chat, screen sharing
phase-3   frontend rewritten in React + TypeScript
phase-4   backend rewritten as a Go signaling server
phase-5   single-node SFU
phase-6   multi-node routing, auth, monitoring, load test
```

This series stays focused on `phase-4/` for a practical reason:

- Go was the new language I was actively learning
- Phase 4 is realistic enough to matter, but not yet as heavy as the SFU stage
- it contains concurrency, long-lived connections, room state, event flow, and debugging situations that are ideal for learning Go

## If you are new to WebRTC, start with this minimum event flow

You do not need to fully learn SDP, ICE, TURN, and STUN before reading this series.

This minimal flow is enough to begin:

1. a user joins a room
2. the signaling server tells that user who is already there
3. browsers exchange the data needed to establish peer connections
4. once the connection is established, media mainly goes peer-to-peer or through an SFU, not continuously through the signaling server
5. when someone leaves, the server updates room state and notifies the others

Phase 4 in this series mostly focuses on steps 1, 2, 3, and 5.
