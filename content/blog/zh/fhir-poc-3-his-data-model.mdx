> **這篇適合誰**：所有處理過 legacy 系統的工程師——就算你沒碰過醫療，這裡的每一種資料債你都會覺得眼熟。也適合想理解「FHIR 化到底在轉什麼」的資訊主管。

## 假資料的第一原則：要髒得真實

POC 最常見的自欺是用太乾淨的假資料——欄位齊全、格式標準、代碼規範，然後宣稱「轉換沒問題」。真實醫院的資料不長那樣。

所以這個 POC 的模擬 HIS（SQLite + 假資料產生器）刻意保留了台灣 HIS 的在地慣例，**每一條都是 ETL 的考題**：

| HIS 慣例（如實模擬） | 範例 | FHIR 化要做的事 |
|---|---|---|
| 性別存院內代碼 | `sex = '1'`（男） | 代碼翻譯 → `male` |
| 生日存民國年 7 碼 | `0820821` | 格式正規化 → `1993-08-21` |
| 檢驗用院內項目碼 | `GLU-AC` | 術語對應 → LOINC `1558-6`（第 4 篇主角） |
| 血壓一列兩欄 | `sbp=142, dbp=88` | 結構轉換 → 一筆 Observation 帶兩個 component |
| 數值存 TEXT 欄位 | `value = '7.7'` | 型別修復 → `valueQuantity` + UCUM 單位 |
| 頻次/途徑用縮寫 | `BID`、`PO` | 對應結構化 Timing 與途徑 |
| 關聯靠病歷號/就診號 | `chart_no`、`enc_no` | 轉成資源間的 `reference` |

兩個小堅持讓它更「真」：**身分證字號用正確的檢核碼演算法產生**（字軌轉數＋權重加總 mod 10——真實介接會驗格式，假資料也得過關）；**亂數用固定種子**，重跑產生完全相同的資料，這讓下游 ETL 的冪等性可以被驗證。

## 兩種世界觀：HIS 為流程而生，FHIR 為交換而生

把 HIS schema 和 FHIR 資源並排看，差的不是欄位名，是**設計目的**。

HIS 的資料模型是這家醫院「作業流程與健保申報邏輯」的化石層：`encounters` 表有科別代碼是因為申報要填；`lab_results` 有簽發醫檢師欄位是因為評鑑要求報告有人負責。它很合理——但只在這家醫院內合理。

FHIR 把同一批事實重組成一張以病人為根、每個節點自帶完整語意的資源圖。其中最有代表性的觀念轉換是：**HIS 的一列不一定等於一個 FHIR 資源**——

- `lab_results` 一列 → 一筆 `Observation`（一對一）
- `vital_signs` 一列 → **最多五筆** `Observation`（血壓一筆帶兩個 component，體溫、心率、身高、體重各一筆）
- 轉 `lab_results` 時還會**長出**別的資源：簽發醫檢師欄位是個字串，但 FHIR 裡「人」是一等公民，必須先建 `Practitioner` 資源再用 reference 指過去

第三點揭示了 mapping 工作的本質：**它不是逐表轉換，是把關聯式模型重組成資源圖**，而且有依賴順序——人員、機構這些「目錄類資源」是所有臨床資源的地基，要先建。

## 髒資料的分級處理：檢驗室 SOP 的工程版

如果 HIS 裡有一筆生日 `0080230`——民國 8 年 2 月 30 日，不存在的日期，但老系統裡真的會有——ETL 該怎麼辦？

選項有三：(a) 跳過整個病人、(b) 丟掉生日照傳、(c) 擋下來人工處理。

我在檢驗科的直覺是 (c)：儀器回傳異常值時，我們不會猜一個值發報告，也不會假裝沒看到——擋下來，人工複核。這個 SOP 直接翻譯成了 ETL 的設計原則：

```
關鍵欄位（身分證、生日、檢驗值）不合格 → 擋下，進 rejected 清單，非零 exit code
選填欄位缺失 → 用 FHIR 的 data-absent-reason 明確標注「缺失及原因」
永遠不做的事 → 猜值、靜默丟棄
```

**擋下率是專案健康指標**：初期高是正常的，那不是 ETL 的失敗，是它在替醫院盤點歷史債——每一筆被擋下的資料，都是一筆遲早要還的帳。

## 一個「重跑才現形」的 bug

收尾前分享一個真實 bug。ETL 設計成冪等（重跑不產生重複資料，細節見第 5 篇），最終驗證時卻發現：重新產生假資料後再跑 ETL，一批資源被當成「新資料」建立了。

原因在 SQLite：`AUTOINCREMENT` 的序號存在 `sqlite_sequence` 表，`DELETE FROM` 清空資料**不會重置序號**。重新 seed 後，`lab_results` 的 id 從上次的尾端續號，下游依 id 產生的 FHIR 資源 id 跟著漂移——冪等性無聲地碎了。

```sql
-- seed 腳本的修正：清資料之外，也要歸零序號
DELETE FROM lab_results;
DELETE FROM sqlite_sequence;   -- 少了這行，deterministic id 就不 deterministic
```

這種 bug 不會在「跑一次」的 demo 裡出現，只有完整的 end-to-end 重跑才逼得出來——**POC 的價值不在做出來，在驗出來**。

> **決策者視角**：FHIR 化專案的時程風險，最大宗不是 FHIR 本身，而是本篇這些歷史債的量。立項前先做「資料品質盤點」（抽樣檢查關鍵欄位的髒資料率），估出來的時程會準得多。
