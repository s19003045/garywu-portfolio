最近我開始用一個 WebRTC 專案學 Go。

這裡的重點其實不只是 WebRTC，也不只是 Go 語法本身，而是我想刻意練習一件事：**在 AI agent 盛行的時代，怎麼更主動地學一門新語言。**

如果放在以前，遇到一門新語言，常見做法通常是買一本書、找一套教學、把基礎語法一路讀完，再慢慢寫小練習，最後才碰到真實專案。這種方法不是錯，只是成本很高，而且常常要花掉數個月。

對已經在做工程的人來說，這條路不一定最適合。因為實務上更常見的情境是：專案已經在眼前，問題已經在眼前，我需要在理解架構與持續交付之間，快速建立「足夠可靠的理解」。

這也是我想寫這個系列的原因。它不只是記錄我怎麼學 Go，也想示範一件事：如果你手上也有一個陌生語言的專案，AI agent 可以怎麼陪你從看不懂，到開始能問對問題、驗證理解、逐步建立判斷力。

如果你是第一次接觸這個專案，建議先讀這篇前導文：[讀這個 Go 系列前，先看懂 WebRTC 專案在做什麼](/zh/blog/webrtc-poc-go-series-primer)。

## 這個系列適合誰看

這個系列比較適合下面幾種讀者：

- 已經在做工程，但 Go 對你仍然陌生
- 想學的不只是語法，而是怎麼讀懂真實專案
- 已經開始用 AI agent，但不想只把它當程式碼代工
- 想知道怎麼把追問、驗證與除錯也納入學習流程

如果你要的是完整 Go 教材，這個系列不會是最全面的選擇。

但如果你想看一段比較接近真實工作的學習過程，它應該會比純語法型內容更貼近實戰。

## 先補一個必要背景：這個 Go 專案到底是做什麼的

如果你本身不熟 WebRTC，直接讀後面的文章，確實很容易卡住。因為這個系列預設的教材，不是一個孤立的 Go 練習題，而是一個分階段演進的 WebRTC POC。

這個 repo 不是一開始就用 Go，也不是一開始就做 SFU。它是從最小可行的 1 對 1 通話開始，逐步往多人、React 前端、Go 後端、SFU 與多節點架構演進。

我這個系列聚焦的是 **Phase 4**。這一階段做的事是：

- 前端沿用 React + TypeScript
- 後端把原本的 Node signaling server 改寫成 Go
- WebSocket 路徑與信令協議保持相容
- 讓學習重點集中在 Go 的併發模型、連線生命週期與狀態管理

如果再講白一點，這個 Go 專案不是在處理影音編碼本身，而是在處理 WebRTC 連線建立前後所需的 **信令交換**：誰加入房間、誰要跟誰建立連線、offer/answer/ICE candidate 要怎麼轉送。

少了這個背景，讀到 `join`、`signal`、`leave`、`readPump`、`Hub` 這些詞時，就會覺得它們像是突然出現的內部名詞。先知道專案在解什麼問題，後面的閱讀阻力會少很多。

## 如果你想對照完整程式碼，先從這裡開始

這個系列會節錄最關鍵的片段，但如果你想一邊看文章、一邊對照完整程式碼，我建議直接搭配 repo 一起讀：

- Repo: [webrtc-poc](https://github.com/s19003045/webrtc-poc)
- 專案總覽：`README.md`
- 本系列對焦階段：`phase-4/README.md`
- Go server 進入點：`phase-4/server/main.go`
- 房間狀態與事件處理：`phase-4/server/hub.go`
- WebSocket 讀寫生命週期：`phase-4/server/client.go`
- 信令資料結構：`phase-4/server/message.go`

如果你只想先建立最小地圖，可以先把它想成下面這樣：

```text
webrtc-poc/
├─ README.md
├─ phase-3/
│  └─ client/        # React + TypeScript 前端
└─ phase-4/
	├─ README.md
	└─ server/
		├─ main.go     # HTTP / WebSocket 入口
		├─ hub.go      # 房間狀態、join/signal/leave
		├─ client.go   # readPump / writePump
		└─ message.go  # 訊息格式
```

你不用一開始就把整個 repo 讀完。先知道這幾個檔案各自負責什麼，後面的每一篇文章就比較容易定位自己在看哪一層。

## AI 改變了學習入口，但沒有取代學習本身

現在的 AI agent 很容易先幫你做兩件事：

1. 先產出一份可執行的程式碼
2. 先整理出程式的大致控制流程

這讓新語言的學習入口跟以前不一樣了。

以前的入口是語法教材。

現在的入口，常常可以直接是**一個真的跑得起來的專案**。

但這不代表學習變得自動化。AI 不會把理解直接塞進腦袋裡。它可以先給我起點，但真正的學習仍然來自幾件事：

- 我能不能把問題拆小
- 我能不能指出自己到底哪裡不懂
- 我能不能透過追問，把模糊理解修正成清楚理解
- 我能不能回到程式與執行結果驗證自己的判斷

所以我愈來愈覺得，AI 真正帶來的不是「不用學了」，而是**可以換一種更接近實務的學法**。

## 我這次刻意採用的學法

這次學 Go，我不是先找一套完整教材。我是直接拿一個 Go 寫的 WebRTC signaling server 當教材，然後把 AI agent 當成程式教練。

做法很簡單，但心態上跟把 AI 當代工工具差很多。

我沒有要求 AI 一次把全部講完，而是讓它陪我做下面幾件事：

1. 先從進入點開始，告訴我這個專案從哪裡跑起來
2. 只用一小段程式碼，解釋一個概念
3. 在我回答之後，再指出我哪裡理解得不夠精準
4. 把抽象概念綁回真實程式，而不是只講定義
5. 在我做出第一個理解後，要求我用自己的話重述
6. 最後再回到 log、執行結果、錯誤訊息做驗證

這個過程很像在請一個教練帶讀程式，而不是請一個工具直接幫我生成答案。

## 這個系列想保留的，不只是答案

很多文章只會留下整理後的結論。

但我這次覺得最有價值的，反而是那些中間過程：

- 我一開始怎麼理解錯 pointer
- 我怎麼搞混 close channel 與 close connection
- 我為什麼以為是 writePump 先發現斷線
- 我怎麼透過追問與 log，慢慢把理解修正回來

這些過程很重要，因為真正的學習，常常不是從「看見正確答案」開始，而是從「發現自己原本哪裡想錯」開始。

所以這個系列不會是完整貼出一長串 AI 對話，而是會保留那些真正幫助理解發生的互動片段，並補上我自己的註解：

- 我當時為什麼這樣問
- AI 的回答哪裡有幫助
- 哪裡還要再追問
- 我最後怎麼把它消化成自己的理解

我想保留的不是「AI 說了什麼」本身，而是**理解怎麼一步一步成形**。

## 這個系列會寫什麼，不會寫什麼

我會寫的是：

- 怎麼從真實專案讀懂 Go 的進入點
- goroutine、channel、Hub 在這個專案裡到底怎麼配合
- WebSocket 連線生命週期怎麼走
- signaling 事件怎麼在 server 裡流動
- 我怎麼用最少的 log 讀懂服務行為
- 我怎麼把 AI agent 當學習教練，而不是答案產生器

我不打算寫的是：

- Go 語法大全
- 教科書式入門課程
- 完整逐字的 AI 對話紀錄
- 脫離專案脈絡的零碎知識點

也就是說，這個系列比較像一段**工程師的互動式學習紀錄**，而不是一套全面課程。

它的重點不是替代教材，而是補足一種教材通常不會完整呈現的東西：從陌生、誤解、追問、驗證，到逐步內化的過程。

## 我真正想回答的問題

這整個系列真正想回答的，不是「Go 該怎麼學才標準」，而是：

**在 AI agent 時代，我們能不能用更主動、更有意識的方法，學會一門新語言，而不是只拿到它產生的答案？**

如果可以，那真正重要的能力就不只是寫出程式碼，而是：

- 你能不能問出對的問題
- 你能不能分辨自己哪裡還沒真的懂
- 你能不能把 AI 給的答案，轉成自己的理解與判斷

這也是我想把這段過程寫下來的原因。

如果這個系列有價值，我希望它的價值不只在於「我整理了什麼」，也在於「別人看完後，可以拿去複製這種學法」。
