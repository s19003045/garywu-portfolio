> **這篇適合誰**：醫院資訊部門主管（這是為你寫的）、要評估醫療專案的決策者，以及想理解「技術以外那一半」的工程師。前六篇解決「怎麼做」，這篇面對「怎麼落地」。

## 困難在哪：三個面向的誠實盤點

### 技術面

**Legacy HIS 是黑盒子。** POC 的模擬 HIS 是自己蓋的，schema 一目了然。真實醫院的 HIS 可能是 20 年前的系統：文件散佚、欄位意義只存在資深工程師腦中、廠商不開放 API。盤點資料在哪裡、長什麼樣，往往就吃掉專案前三分之一的時間。

**資料品質比想像糟。** 民國 8 年 2 月 30 日這種日期真的存在。同一病人多個病歷號、單位改了三次但舊資料沒跟著改——FHIR 化是一面照妖鏡，所有歷史債都會在 ETL 的擋下清單裡現形。

**術語對應是人力黑洞。** POC 對應 10 個檢驗項目；真實醫院是數千項檢驗、上萬筆藥品，且需要臨床專業判斷（第 4 篇）。這是全專案最無法壓縮工期的環節。

**資安與個資。** FHIR 讓資料「好交換」的同時也讓資料「好外洩」。授權（SMART on FHIR）、稽核軌跡、去識別化，每一項在正式環境都是必答題。

### 組織面（通常比技術面更難）

**HIS 廠商的商業結構。** 台灣多數中小醫院的 HIS 是外包的，廠商模式是「改一支介接收一次費」；標準化長期壓縮這塊收入，配合意願天然有限。合約有沒有「資料可攜」條款，直接決定專案成本。

**資訊室的人力現實。** 以維運為主、開發能量有限，同時背著健保申報改版與評鑑作業的硬時程。沒有專職人力，FHIR 專案就會變成「有空再做」。

**先行者困境。** 交換標準的價值來自「大家都用」：第一家導入的醫院拿不到跨院交換的好處，只承擔成本。單靠個別醫院的商業理性推不動，政策誘因至關重要。

**雙背景人才稀缺。** 懂 FHIR 的不懂檢驗流程，懂臨床的不懂 REST API——需求轉譯與驗收把關都卡在橋樑人才上。

### 標準面

TW Core 仍在演進（0.3.2 → 1.0.0 之間就有破壞性變更），升版需要回歸驗證機制；IG 覆蓋不到的在地需求要用 extension，但 extension 一多就回到不互通的老路——需要「原生優先、extension 是最後手段」的治理紀律；健保申報等既有格式短期不會消失，FHIR 是**多一軌**而不是**換一軌**。

## 七項策略

**1. 垂直切入，單一使用案例打穿全鏈。** 不要啟動「全院 FHIR 化」這種大到必敗的專案。選一個價值明確、範圍可控的案例——檢驗報告交換是經典首選（結構化程度最高、LOINC 成熟、跨院需求真實）——把整條鏈打穿。本系列的 POC 就是這條路徑的縮小版。

**2. 旁掛 CDR，不動 HIS。** 與廠商談判的標的從「改造系統」縮小為「提供資料出口」；FHIR Server 用成熟開源或雲端方案，自建 server 不是醫院該打的仗（第 2 篇）。

**3. 資料品質分級。** 關鍵欄位不合格就擋下進人工佇列；選填欄位缺失用 `data-absent-reason` 標注；擋下率當專案健康指標——初期高是正常，它是在替醫院還歷史債（第 3 篇）。

**4. 術語治理制度化。** 成立對應工作小組（資訊＋檢驗＋藥劑＋病歷共審，如同檢驗報告要有簽發者）；對照表用 ConceptMap 資源存進 server（版本、稽核、`$translate` API 免費獲得），不要散在 Excel 裡（第 4 篇）。

**5. 驗證自動化，合規進 CI。**「符合 TW Core」必須是機器判定並進 CI：mapper 每次改動、IG 每次升版，全量回歸。同時記住合規 ≠ 正確——臨床合理性檢核（delta check、極端值）要另建一層（第 5 篇）。

**6. 分階段路線圖，借力政策。** POC → Pilot（單科、真實資料、小範圍）→ 擴大 → 常態營運，每階段有量化指標（擋下率、驗證通過率、查詢延遲）。同時對齊衛福部計畫與評鑑誘因，讓專案掛上政策列車，緩解先行者困境。

**7. 投資橋樑人才。** 制度可以買、軟體可以租，雙背景人才只能養。讓臨床背景的同仁學會讀 profile、讓工程師進檢驗科跟一天流程，比多買一套工具更能決定成敗。

## 一頁總結

| 挑戰 | 因應 |
|---|---|
| Legacy HIS 封閉 | 旁掛 CDR、只要資料出口、不動 HIS |
| 資料品質差 | 分級擋關、擋下清單當還債清單 |
| 術語對應量大 | 治理小組＋ConceptMap 資源化＋分批滾動 |
| 廠商配合度 | 合約載明資料可攜、縮小談判標的 |
| 人力與參與 | 垂直小專案、高層支持、政策誘因 |
| 標準演進 | 驗證進 CI、升版回歸、extension 紀律 |
| 先行者困境 | 先做院內價值（資料平台、研究、儀表板），交換價值隨生態到位 |

## 收官

八篇下來，這個系列想留下三句話：

1. **技術上**，FHIR 已經是 Web 工程師的主場——REST + JSON + 開源工具鏈，門檻在領域知識而非工具
2. **方法上**，合規要可機器驗證、資料要分級處理、踩坑要保留成教材
3. **本質上**，FHIR 導入不是資訊專案，是資料治理專案——技術決定它能不能做，治理決定它活不活得下來

而貫穿一切的，是那個最稀缺的角色：能同時聽懂臨床語言和工程語言的人。我用 14 年當醫檢師、再用轉職後的工程師生涯，剛好把這兩種語言都學會了——這個系列，就是我的翻譯練習。
