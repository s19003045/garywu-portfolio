前兩篇（[開放大型平台](/zh/blog/webrtc-poc-8-blueprint-meet-like-platform)、[資安大廠](/zh/blog/webrtc-poc-9-blueprint-secure-enterprise)）都是「互動型、很多中小房（場景 A）」。這篇是完全不同的形狀：**萬人演唱會現場直播**——單一「房間」湧入數萬甚至數十萬人，但**絕大多數只是觀看**，真正在發送的只有舞台上少數人。

這個場景最重要的判斷，在第一篇就講過：**不要把所有人都塞進 WebRTC**。它的正解是「廣播」，不是「互動」。

> 一樣是「若目標是這個場景，我會這樣做」的規劃。

## 1. 場景與硬限制

- **規模形狀**：單一超大房（場景 B），觀眾數萬～數十萬同時在線。
- **互動 vs 廣播**：**廣播為主**。發布者（舞台鏡頭/音控）只有少數；其餘全是觀看。
- **延遲可放寬**：純觀看下，數秒延遲完全可接受——這正是換取無限規模的籌碼。
- **成本敏感**：主成本是 **CDN 流量**，跟觀眾數直接相關。
- **入場控制**：要驗票，只有買票的人能看。
- **不可妥協**：撐得住瞬間湧入的海量並發、播放要順、票券要擋得住盜看。

把「大多數人不需要互動」這件事認出來，整個架構就豁然開朗。

## 2. 參考架構（兩層：接入 + 分發）

```
  舞台來源(少數)                      分發(海量)
  攝影/音控 ─WebRTC/SRT/RTMP─▶ ┌──────────┐  推流  ┌─────────┐  拉流
                              │ 轉碼/打包 │──────▶│  CDN     │──HTTP──▶ 觀眾(HLS player)
                              │ ABR + LL- │       │(origin→  │
                              │  HLS/CMAF │       │  edge)   │
                              └────┬─────┘       └─────────┘
                                   │ 錄影
                                   ▼
                              VOD 儲存(回放/DVR)

  另外:票務/Auth ── 簽名 URL/Cookie ──▶ 只有持票者能向 CDN 拉流
        聊天/互動 ── 獨立可擴展的訊息系統(與媒體分開)
```

關鍵：**接入端用即時技術（少數人），分發端用串流 + CDN（海量人）。** 兩端解耦。

## 3. 媒體層（深）：兩層完全不同的技術

**(a) 接入 / 製作端（少數發布者）**
- 舞台來源可走 **WebRTC/SFU**（要低延遲協調時）或 **SRT / RTMP**（專業製作常用，穩定、容錯）。
- 多路來源先在媒體伺服器**匯流成一路節目訊號**（導播切換、混音、疊字幕）。

**(b) 分發端（海量觀眾）**
- 把節目訊號**轉碼成多檔位（ABR ladder）**：例如 240p~1080p 多種畫質，讓播放器依網路自動切換。
- **打包成 LL-HLS / CMAF**，推到 **CDN**；觀眾用 HTTP 拉流。CDN 邊緣節點可水平擴展到任意規模——**這就是規模與成本脫鉤的關鍵**。
- 延遲：LL-HLS 約 2~5 秒，對演唱會完全夠用。
- **不是** 每個觀眾開一條 WebRTC。真要給 VIP 一小撮人「秒級互動」，才另開一個小的低延遲 WebRTC 層。
- 韌性：**origin shielding**（保護源站不被打爆）、**多 CDN**（單一 CDN 故障可切換）。

## 4. 身分與存取（深）：驗票，不是帳號

- **票券驗證**：不是傳統登入，而是「買票 = 入場權」。票務系統簽發一張綁定「這場活動 + 票種」的入場憑證。
- **簽名 URL / Cookie**：播放器拿憑證換取**有時效的簽名串流網址**（或簽名 Cookie），只有持票者能向 CDN 拉到流。
- **防共享**：每張票限制並發數（同一張票同時只能在 N 個裝置播），避免一票多人看。
- **進階**：高價場可加 **DRM**（Widevine / FairPlay）。

## 5. 資料與合規

- **內容版權**：演出內容的授權與地域限制（**geo-blocking**：某些地區不可播）。
- **DRM**：需要時用，防錄製外流。
- **浮水印**：嵌入觀眾 ID，盜錄可溯源。
- **回放 / DVR / VOD**：直播同時錄製，提供活動後點播。

## 6. 前端 / UX

- **HLS 播放器**（hls.js / 原生），**ABR 自動切畫質**、低延遲模式。
- **DVR / 時移**：可往回看剛剛漏掉的段落。
- **聊天 / 互動**：海量人數下，聊天**另走一套可擴展的訊息系統**（pub/sub），且通常要抽樣/限流呈現，否則畫面洗到看不了。
- **直播狀態**：「LIVE」標示、字幕、觀看人數。

## 7. 可觀測性、維運與成本

- **CDN 流量是主成本**：≈ 觀眾數 × 位元率 × 時長。這是這個場景唯一要死盯的數字。
- **QoE 指標**（從播放器回傳）：卡頓率（rebuffering）、起播時間、畫質切換次數——這才是「觀眾體驗好不好」的真實量測。
- **省錢槓桿**：ABR ladder 設計、用更省的編碼（HEVC/AV1 降位元率）、CDN 分級計價、多 CDN 議價、必要時 P2P 輔助分發。

## 8. 主要風險與失效模式

| 風險 | 失效樣子 | 緩解 |
|---|---|---|
| 開場瞬間湧入 | 源站被打爆、觀眾起播失敗 | origin shielding、CDN 預熱、分層快取 |
| CDN 故障 | 整場觀眾斷流 | 多 CDN、即時切換 |
| 接入端中斷 | 舞台訊號斷、直播中斷 | 備援編碼器/雙路接入 |
| 盜看 / 盜錄 | 一票多人、外流 | 並發限制、DRM、浮水印、簽名 URL |
| 聊天洗版 | 海量訊息壓垮前端 | 獨立訊息系統 + 限流/抽樣 |

## 9. 技術棧速覽

- **接入**：WebRTC/SFU 或 SRT/RTMP（專業製作）。
- **製作**：導播/混流媒體伺服器。
- **轉碼/打包**：轉多檔位 ABR + LL-HLS/CMAF 打包器。
- **分發**：多 CDN（origin → edge）。
- **播放器**：hls.js / 原生 HLS。
- **入場**：票務系統 + 簽名 URL/Cookie（+ 可選 DRM）。
- **互動**：可擴展 pub/sub 訊息系統（聊天/反應）。
- **觀測**：播放器 QoE 分析 + CDN 用量監控。

---

把三個場景並排看，最大的收穫不是「學會某個技術」，而是看見**同一個「視訊系統」的字眼，背後其實是三個不同的產品**：Meet 類靠 SFU + 多房分散，大廠靠地端 + 合規，演唱會靠廣播 + CDN。從目標出發，技術自然就被挑出來了——這也是整個 `webrtc-poc` 系列，從「開鏡頭」一路走到「怎麼抉擇、怎麼落地」最想留下的東西。

## 名詞小抄

- **LL-HLS / CMAF**：低延遲的 HTTP 串流格式，適合大規模直播。
- **ABR ladder**：同一內容的多種畫質檔位，讓播放器依網路自動切換。
- **SRT / RTMP**：專業直播接入常用的傳輸協定。
- **origin shielding**：在源站前加一層快取，避免海量請求直接打爆源站。
- **DRM / geo-blocking**：數位版權保護 / 地域播放限制。
- **QoE**：使用者實際感受的播放品質（卡頓、起播、畫質切換）。
