完成 1:1 通話後，很自然會想問下一個問題：能不能把它擴成多人？

直覺上，答案好像很簡單。既然兩個人可以連，那三個人、四個人，不就是多建立幾條連線嗎？

Phase 2 做的就是這件事：把 1:1 P2P 推進到多人 mesh，再加上聊天、螢幕分享、房間成員列表與 TURN。

功能上，它是可以成立的。

但也正因為它成立，mesh 的限制才會變得更具體。

這篇先記一件事：mesh 可以做多人通話，但人數一多，每個人都會一起背更多連線和上傳成本。

## 先用白話理解

多人通話不是把單人通話複製幾次而已。只要多一個人，房間裡每一台裝置都要多維護一些連線與上傳流量。

你可以先把 mesh 想成「大家彼此都直接打電話」，人一多，線路與負擔就會一起膨脹。

![多人 Mesh 架構的連線與上傳成本示意圖，說明 WebRTC 在多人通話時的第一個上限](/post_image/多人通話為什麼不能只靠%20Mesh：WebRTC%20架構的第一個上限.png)

## Mesh 的成本不是線性增加

在 mesh 架構裡，每個人都要和房間裡其他人建立一條 PeerConnection。

如果房間有 N 個人，每個人要維持 N-1 條連線。更重要的是，每個人不只要接收多路影像，也要把自己的影像上傳 N-1 份。

這在 3 到 5 人時還可以當作 POC，但人數一多，成本會非常快地放大。

真正的問題不是「能不能連」，而是「連了之後是否還能穩定」。

## 功能越多，狀態越難管理

Phase 2 也加入了 DataChannel 文字聊天與螢幕分享。

DataChannel 本身很有趣，因為它讓資料傳輸可以走在 WebRTC 連線上，不需要另外打一條 HTTP API。但這也代表每個 peer 之間的資料通道都要被建立、監聽與清理。

螢幕分享則讓狀態管理更複雜。使用者不是只開關麥克風和鏡頭，還可能在通話中替換 video track。這時候你要處理的不只是 UI 狀態，而是既有 PeerConnection 裡的 sender、track replacement 與遠端畫面更新。

也就是說，多人通話的複雜度不是只來自「多幾個人」，而是每個功能都會乘上每個 peer 的生命週期。

## TURN 解決的是連通性，不是架構上限

加入 TURN 之後，另一個界線也變清楚了。

TURN 可以解決嚴格 NAT、企業網路或 P2P 無法直連的問題。它是 WebRTC 實務上很重要的一塊，因為沒有 TURN，很多真實網路環境下的連線成功率會不穩。

但 TURN 不會讓 mesh 變成可擴展架構。

TURN 解決的是「連不連得上」，不是「多人時成本會不會爆」。如果每個人仍然要上傳 N-1 份影像，TURN 只是讓這些連線更有機會成立，不會改變頻寬模型。

## 這個階段真正的價值

Phase 2 的價值，不是證明 mesh 可以拿來做正式多人會議。

相反地，它的價值是讓我親手感受到 mesh 為什麼有上限。

如果只看架構文章，很容易知道 SFU 比 mesh 更適合多人。但自己做過 mesh 之後，才會更清楚：

- 每個使用者加入，都會影響房間內所有人的連線
- 每個人離開，都要正確清理多條 PeerConnection
- 每個媒體功能，都要考慮多 peer 同步
- TURN 只能改善連通性，不能消除 mesh 的上傳成本

## 不急著跳到 SFU 的原因

從結果看，既然 mesh 有明顯上限，那是不是一開始就應該用 SFU？

如果目標是做正式產品，答案可能是。

但如果目標是理解 WebRTC，我反而覺得 Phase 2 很必要。因為 SFU 會把很多複雜度移到 server，如果沒有先理解 peer connection、track、candidate、renegotiation 與房間狀態，後面做 SFU 時反而更難判斷問題出在哪裡。

這也是這個專案分 phase 的原因。

不是因為每個 phase 都是最終解，而是每個 phase 都刻意暴露一種限制。

Phase 2 暴露的限制很清楚：mesh 可以做出多人通話，但它不是規模化的答案。

## 名詞小抄

- **PeerConnection**：瀏覽器之間建立 WebRTC 連線的核心物件。
- **DataChannel**：在 WebRTC 連線上傳資料，不一定傳影音。
- **TURN**：當雙方無法直接連線時，用來中繼流量的伺服器。
- **Mesh**：每個人都直接和房間裡其他每個人連線的架構。
