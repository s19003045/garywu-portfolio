> **這篇適合誰**：對前端效能、WebAssembly、3D 視覺化或即時資料系統有興趣的工程師。
> **讀完你會知道**：怎麼在瀏覽器裡即時傳播上萬個物件而不掉幀、資料密集的前端該怎麼切工作執行緒、以及為什麼我認為「先量測、實測、標示自己不知道什麼」比任何架構圖都重要。

先講清楚我做了什麼：一個叫 **ORBITAL WATCH** 的平台，用太空視角的 3D 地球，即時呈現全球 **18,688 個在軌物件**——衛星、火箭本體、軌道碎片——此刻各自在哪裡。每一個物件的位置都是在你的瀏覽器裡、用標準的 SGP4 軌道模型逐幀算出來的，不是預先錄好的動畫。

這個念頭其實很單純：軌道資料是公開的（CelesTrak 每天更新全球目錄），SGP4 是幾十年的成熟演算法，Cesium 能畫出真實的 WGS84 地球。把這三樣接起來，理論上就能做出一個「太空版的 Google Earth，但看的是衛星」。難的從來不是這個概念，而是**規模**——把一顆衛星畫出來很簡單，把一萬八千顆同時算、同時畫、還要維持流暢，是完全不同的工程問題。

這篇就是那個工程問題的建置紀錄。

## 這個平台在做什麼

在往下講架構之前，先讓你知道最後長成什麼樣子：

- **太空視角地球**——Cesium 打造的 WGS84 橢球，有由時鐘推算的真實日夜晨昏線、大氣輝光與星空背景。
- **全量即時追蹤**——18,688 個物件同時傳播，不是取樣、不是子集。含 2,622 個軌道碎片。
- **目標遙測**——點任一顆衛星，即時顯示經緯度、高度、軌道速度、完整的軌道根數，以及來自 SATCAT 的身分資料（屬於哪一國、何時發射、雷達截面積多大）。
- **地面站過境預報**——對指定觀測站算出未來 24 小時的過境，而且會誠實區分「肉眼看得見」與「只能用無線電追蹤」。
- **導航星座幾何**——即時計算 GPS/北斗/Galileo/GLONASS 的定位精度因子（DOP）。
- **時間控制**——1× 到 3600× 加速，可以看著軌道面隨地球自轉進動。

技術棧一句話：**CesiumJS（3D 地球）+ satellite.js 的 WebAssembly SGP4（軌道傳播）+ Web Worker（隔離運算）+ Fastify（只做資料代理與快取的輕量後端）**。

真正決定這個平台成不成立的，是這幾樣東西怎麼組合。而這個組合，是量測出來的，不是我一開始就想好的。

## 第一個決定：先量測，再選架構

我沒有先畫架構圖。我先寫了一段最笨的程式：把 CelesTrak 的完整目錄抓下來，用純 JavaScript 的迴圈，對每一顆衛星跑一次 SGP4，量它要花多久。

因為在動任何架構之前，我需要知道一個數字：**在瀏覽器裡把全部衛星傳播一次，到底有多貴？** 這個數字會決定一切——如果夠便宜，放主執行緒就好；如果很貴，就得想辦法把它移開。

結果是這樣（16,063 顆，當時的目錄規模）：

| 方式 | 每幀傳播全部衛星的耗時 |
|---|---|
| 純 JavaScript 迴圈 | 約 79 ms |
| WebAssembly 批次傳播器 | 約 16 ms |

79 毫秒是什麼概念？瀏覽器要維持 60fps，每一幀只有 **16.7 毫秒**的預算。純 JS 光是算位置就吃掉了將近五幀的時間——放進主執行緒，畫面直接卡死。

`satellite.js` 這個函式庫提供了一個 WASM 的 `BulkPropagator`，把整批衛星一次丟進去用 SIMD 平行算。同一批資料，16 毫秒。快了五倍。

但 16 毫秒仍然是主執行緒每幀預算的全部。所以真正的決定是兩層的：

> **把傳播用 WASM 加速，再整個搬進 Web Worker。** WASM 讓運算變便宜，Worker 讓它完全離開主執行緒——這樣主執行緒就一整幀都空出來給 Cesium 算繪。

這個「先量測、再讓數字決定架構」的順序，是我做這個專案最重要的一個習慣。如果我一開始就憑感覺搭一套架構，很可能會過度設計，也可能低估某個環節的成本。量測讓我知道瓶頸具體在哪、有多大，架構是回應那個數字長出來的。

## 資料從哪來：CelesTrak、SATCAT 與一個只做快取的後端

軌道資料來自 [CelesTrak](https://celestrak.org/)——它每天更新全球在軌物件的 GP/OMM 根數。但我不能讓每個使用者的瀏覽器直接去打 CelesTrak：一來有 CORS 問題，二來 CelesTrak 明確要求用戶端至少快取兩小時，否則會被封鎖。

所以後端存在的唯一理由，就是**當一個懂規矩的代理**：定時抓取、落地快取、正規化成前端好用的 JSON。它沒有資料庫，重啟就重抓。

一開始我只載入現役衛星，但軌道環境裡最重要的一塊其實是**碎片**。CelesTrak 的公開服務不給你單一的完整目錄查詢（我試過 `GROUP=full`，直接被拒），但它以專門分組的形式提供了幾大碎片雲。我把它們聚合進來：

- 風雲一號 C 碎片 1,919 個——2007 年的反衛星試驗，史上單一事件產生最多可追蹤碎片
- Cosmos 2251 與 Iridium 33 碎片共 700 多個——2009 年史上首次兩顆衛星在軌相撞

這四起正是人類製造的最重大軌道碎片事件。目錄因此從 16,063 擴充到 **18,688** 個物件。

![以「碎片雲」著色時，風雲一號 C 反衛星試驗產生的碎片在約 800 公里的近極軌道形成清晰的紅橙色殼層，明顯高於主要衛星群](/post_image/orbital-watch-debris-clouds.png)

我還接上了 CelesTrak 的 SATCAT 詮釋資料，補上 GP 根數裡沒有的身分維度——屬於哪一國、發射日期與場地、雷達截面積。全部 18,688 個物件都成功聯結上。有個意外但正確的副作用：接上碎片後，中國的在軌物件數從 1,445 跳到 3,364，因為反衛星試驗的碎片在 SATCAT 裡歸屬於原擁有國。

後端還有一個容易被忽略的效能問題。完整目錄約 6.7 MB，一開始我的 API 每次請求都重新把它 JSON 序列化、再重新 gzip 一遍。但目錄三小時才實質變動一次，這些工作沒有理由每次都重做。

> **把只變一次的東西，只算一次。** 我改成在目錄建立時就一併完成序列化、gzip、brotli 與 ETag 計算，路由只負責挑編碼後直接送出位元組。

回應時間從 61 毫秒降到 **4 毫秒**。這不是什麼高深的技巧，就是認出「這個成本被放在了錯的地方」。

## 讓 1.8 萬顆點在瀏覽器裡動起來

現在 Worker 裡的 WASM 每 16 毫秒就算好一批新位置。問題是：怎麼把這批資料交給主執行緒，而且不製造新的瓶頸？

每一幀，Worker 要把 18,688 個物件的位置（各三個座標）交給主執行緒——那是接近 400 KB 的資料。如果用一般的訊息傳遞，這 400 KB 會被**複製**一次。每秒十幾次、每次幾百 KB 的複製，加上隨之而來的垃圾回收，會把剛剛省下的效能又吃回去。

解法是 Transferable Objects——把 `ArrayBuffer` 的所有權直接**轉移**給主執行緒，零複製。但轉移之後，Worker 這一側的緩衝區就失效了。所以我讓主執行緒用完之後，把同一批緩衝區**交還**給 Worker 重複使用：

```typescript
// Worker 回傳位置時，把緩衝區所有權轉移出去（第二個參數）
self.postMessage(
  { type: 'frame', positions, geodetic, valid },
  [positions.buffer, geodetic.buffer, valid.buffer],
);

// 主執行緒用完後，下一次請求時把同一批緩衝區交還 Worker
worker.postMessage(
  { type: 'propagate', recycle: { positions: buf1, geodetic: buf2 } },
  [buf1, buf2],
);
```

這個緩衝區循環讓整條資料流幾乎不配置新記憶體，長時間執行也不會有 GC 抖動。

而這個設計，也直接製造了我這個專案踩到的第一個真正的 bug。

主執行緒收到緩衝區後會立刻把點畫好，這一步是同步的、沒問題。但我還有一個每 250 毫秒取樣一次的 UI 更新器，它會**稍後**才去讀那批位置資料填進遙測面板。問題是——那時候緩衝區早就被交還給 Worker、已經 detached 了。讀出來是 `undefined`，`.toFixed()` 直接炸掉，整個右側遙測面板連同過境預報一起崩潰。

這個 bug 的陰險之處在於，地球上的點**照樣在動**——因為畫點那一步是同步的，正常運作。壞掉的只有事後才讀資料的那部分。修法是讓場景管理器自己持有一份穩定的副本，任何「稍後再讀」的程式碼一律向它查詢，而不是去碰那批隨時會被回收的緩衝區。

## 太空視角：地影、可見過境、都卜勒

有了穩定的每幀位置，就能在 Cesium 上疊出真正有資訊量的圖層。

我最喜歡的一個功能是**地影判定**。satellite.js 能算出每顆衛星此刻被地球陰影遮蔽的比例（0 = 完全受照，1 = 完全在本影中）。我用它把進入地影的衛星畫暗。這不只是好看——**地影中的衛星肉眼根本看不見**，這件事是判定「肉眼可見過境」的前提。

而地影，又給了我第二個 bug。

我一開始用透明度來表現亮度衰減：受照的衛星全亮，地影裡的漸暗。邏輯正確，但地影比例每一幀都在微幅變動，導致 18,000 個點的顏色**幀幀都不一樣**。Cesium 因此必須每一幀重寫整份顏色頂點緩衝區——更新率從 15Hz 直接掉到 7Hz。

修法很簡單，但要先想通問題出在哪：

> **把連續變動的量，量化成有限的階數。** 我把亮度量化成 24 階。絕大多數衛星的地影階數在相鄰幀之間完全相同，顏色寫入因此幾乎全部省下，更新率回到 14Hz，而視覺上看不出任何差別。

順帶一提，在做這個功能時我還發現，我先前為了效能把點的混色模式設成「不透明」——那個設定會讓透明度暗化完全失效。效能最佳化和後來的功能需求，有時候會互相打架。

![即時天空狀態面板：本站太陽仰角 −44.3°（完全暗夜），上空 626 顆衛星，選定的 ISS 都卜勒頻移 +8.17 kHz 對應徑向速度 −5.596 km/s（接近中）。地影中的衛星以灰色呈現](/post_image/orbital-watch-sky-doppler.png)

過境預報這一塊，我修正了一個一開始就錯的邏輯。最初我把所有幾何上通過地平線以上的過境都標成「可見過境」。但這對想實際走到戶外看衛星的人是誤導的——肉眼要看得見，還必須同時滿足**衛星本身受陽光照射、而你所在地已經夠暗**（我用天文學的民用曙暮光 −6° 作為分界）。

加上這個判定後，效果立刻顯現：ISS 對臺北未來 24 小時的兩次過境，先前都會被報成「可見」，實際上一次發生在當地下午兩點（天亮）、另一次當地深夜十點但衛星已進入地影——**兩次都不是肉眼看得到的**。這種修正不會讓功能變多，但會讓數字變得可信。

## 三個只有實測才會浮現的錯誤

前面已經講了兩個 bug（緩衝區回收、地影掉幀）。但最有教育意義的是第三個。

我當時剛把大地座標（經緯度、高度）接進遙測面板。畫面上一切正常——衛星在動、數字在跳、高度是對的。我差點就這樣過了。

但我在端對端驗收腳本裡放了一條**物理不變量檢查**：星下點的緯度，絕不可能超過該衛星的軌道傾角。ISS 的傾角是 51.6°，所以它的星下點緯度不可能超過 51.6°。這條檢查抓到 ISS 報出了 **93.3°** 的緯度——地球上根本沒有這個緯度。

追下去發現：satellite.js 的 `GeodeticPositionCalculator` 輸出的分量順序是 `[經度, 緯度, 高度]`，跟單顆版本的 `eciToGeodetic` 剛好相反。我讀錯了順序，把經度當成緯度。全目錄有 **8,141 / 16,063** 顆的「緯度」超過 90°——正好是一半，這正是經緯度對調的特徵。而畫面上，一切看起來仍然正常。

```typescript
// 錯的：以為輸出是 [緯度, 經度, 高度]
geodetic[p]     = radiansToDegrees(geo[p]);     // 其實是經度！
geodetic[p + 1] = radiansToDegrees(geo[p + 1]); // 其實是緯度！

// 對的：BulkPropagator 的輸出順序是 [經度, 緯度, 高度]
geodetic[p]     = radiansToDegrees(geo[p + 1]); // 緯度
geodetic[p + 1] = radiansToDegrees(geo[p]);     // 經度
```

這件事給我的教訓很具體：**視覺化會騙人**。一個在動、看起來合理的畫面，完全不能證明底下的數字是對的。真正能抓到這種靜默錯誤的，是那些「不管實作怎麼寫，物理上都必須成立」的不變量——緯度不超過傾角、經度落在 ±180° 之內、多星座定位精度不會比單一星座差。我後來把這些都寫成了測試。

## 當測試擋下 0.68：錯的是測試，不是程式

講一個相反方向的故事。

平台裡有一項導航星座幾何分析，會算 GPS/北斗/Galileo/GLONASS 的定位精度因子（DOP）——本質是一個 4×4 矩陣的反演。我的驗收測試斷言「合解的 PDOP 必須大於 1」，結果測試擋下了實際算出來的 **0.68**。

![導航星座幾何面板：臺北上空四大 GNSS 合解 PDOP 0.68，北斗以 28 顆可見衛星表現最佳（PDOP 1.01），優於各單一星座](/post_image/orbital-watch-gnss-dop.png)

面對測試失敗，最快的反應是「一定是程式錯了，去修程式」。但我停下來想了一下——**萬一錯的是測試呢？**

我沒有直接改任何一邊，而是寫了一段獨立的驗證程式，用完全不同的方式檢查那個矩陣反演：確認 `反矩陣 × 原矩陣` 等於單位矩陣（誤差 2.22e-16，數值上完美）、確認四顆衛星的幾何給出 PDOP 1.82（符合經典情境）、確認把衛星全擠在天空同一小塊區域會給出 666,891 這種爆炸性的值（正確反映幾何病態）。

結論是：**程式是對的，錯的是我的斷言。**「PDOP 至少為 1」是 GPS 單星座、只能看到四到八顆衛星那個年代的經驗法則。現在四大星座合起來，臺北上空常常有五、六十顆可見，DOP 大致隨可見數的平方根倒數下降，低於 1 是完全正常的結果。我另外算了 59 顆均勻分布的理論值是 0.65，跟平台實測的 0.68 同一個量級。

於是我改的是測試，而且在註解裡寫清楚為什麼——這樣下一個看到 0.68 的人不會重蹈我的懷疑。

> 測試失敗不代表程式錯了，只代表「程式的行為」和「你對正確的預期」對不上。修之前，先確定哪一邊才是對的。

## 我刻意沒有跨過的界線

平台裡有一個功能叫「軌道擁擠度篩查」，會找出此刻彼此距離很近的物件對。它很容易被叫成「碰撞預警」——但我刻意沒有這樣命名。

真正的接近事件評估（conjunction assessment）需要協方差資料才能算出碰撞機率，而公開目錄根本不提供這個。更根本的是，SGP4 對公開根數的位置誤差本身就是公里量級，跟我篩查的門檻同一個數量級。所以這個功能只能誠實地當作「軌道環境有多擁擠」的指標，不能拿來做任何決策。介面上、程式註解裡，我都把這條界線寫清楚。

同樣地，我在文件裡明講碎片資料**並不完整**——CelesTrak 不給完整目錄查詢，SATCAT 列的一萬兩千多個在軌碎片，我只拿得到其中約 2,600 個。

這聽起來像在自曝其短，但我認為這才是工程該有的樣子：

> **一個工程師的價值，有很大一部分在於他能不能清楚地標示出自己不知道什麼、系統做不到什麼。** 一個宣稱能「預警碰撞」但其實只是在比距離的功能，比一個誠實說「這只是擁擠度指標」的功能危險得多。

（有趣的是，篩查第一次跑出來的結果 74% 是雜訊——因為國際太空站的十幾個艙段、加上停靠其上的太空船，共用同一組軌道根數，彼此距離恆為零。排除這些「同一個結構」之後，剩下最接近的一對是中國的 TIANHUI 2-01A 和 2-01B，相距 0.21 公里——那是一對刻意維持次公里間距的編隊飛行雷達衛星。這是真實的軌道現象，正是篩查該呈現的東西。資料的現實，永遠比演算法本身更髒、也更有趣。）

## 打包成一個容器

最後，我把整個平台打包成 Docker，用一個 `docker compose up` 就能跑起來。

這裡有兩個值得一提的決定。第一是**多階段建置**：建置階段裝完整相依、在容器內把前端打包好；執行階段只裝伺服器那五個正式相依，不把 Cesium、React、Vite 這些前端建置工具帶進去。因為前端已經是靜態檔了，執行期完全用不到它們。最終映像維持在 287 MB，而不是把整包 Cesium 塞進去。

第二是用**具名 volume 持久化 TLE 快取**。這不只是慣例——它直接對應到前面說的「CelesTrak 要求至少快取兩小時」。volume 讓容器重啟後沿用既有快取，實測重啟後目錄以 75 毫秒自快取重建，不會每次重啟都去打外部服務。

健康檢查我用 Node 22 內建的 `fetch` 探測 `/api/health`，映像因此連 curl 都不用裝。

## 收尾：這個專案教我的事

回頭看，這個平台真正教我的東西，跟衛星關係不大，跟工程習慣關係很大：

**先量測，再選架構。** 79ms 對 16ms 那個數字，決定了整個 Worker + WASM 的架構。如果我憑感覺搭，很可能會搭錯。

**視覺化會騙人，物理不變量不會。** 一個在動、看起來合理的畫面，證明不了底下的數字是對的。座標對調那個 bug，是「緯度不超過傾角」這條檢查抓出來的，不是我的眼睛。

**測試失敗時，先問哪一邊才是對的。** DOP 那個 0.68，錯的是我的預期，不是程式。花十分鐘獨立驗證，比花十分鐘去「修」一個沒壞的東西划算得多。

**誠實地標示邊界。** 說清楚一個功能不能做什麼、資料缺了哪一塊，不是示弱，而是讓使用它的人不會被誤導。

這些習慣加起來，就是我認為一個系統「可信」的意思——不是它看起來多炫，而是它每一個數字你都能追溯、每一條界線它都替你標好了。
