學新語言時，我覺得最容易被忽略的一件事，是**怎麼除錯**。

因為很多時候，即使你已經大概看懂語法，真正讓理解加速發生的，反而是你能不能把執行中的服務行為看清楚。

這次學 Go，我很快就碰到這個需求。光看 `hub.go`、`client.go` 還不夠，我想知道 join、signal、leave 在執行時到底怎麼流。於是我開始學一件非常實用的事：**只加最少的 log。**

如果你還不清楚 `hub.go`、`client.go` 在整個專案裡的分工，建議先讀前導文：[讀這個 Go 系列前，先看懂 WebRTC 專案在做什麼](/zh/blog/webrtc-poc-go-series-primer)。

這篇的目的也很明確：不是示範一套完整 observability 設計，而是整理一種初學新語言時非常夠用的方法。先用最少、最有辨識度的 log，把程式從「我大概知道它會做什麼」拉到「我真的看得出它現在在做什麼」。

## 我一開始不是不知道怎麼加 log，而是不知道該加在哪裡

其實大部分工程師都會加 log，但初學新語言時很容易落入兩個極端：

1. 幾乎不加，純靠腦內模擬
2. 到處都加，最後整片輸出反而更難看

我這次最有收穫的地方，不是單純加了 log，而是 AI 一直逼我回到一個問題：

**如果只能加 3 個位置，你要加哪裡，才能最大化判讀價值？**

這個問題很好，因為它迫使我思考控制流程的關鍵節點。

也因為問題被壓得夠小，AI 的幫助就變得很具體。它不是告訴我「多印一些看看」，而是逼我先界定：我到底想排除哪一個假設。

## 最有價值的 3 個位置

最後收斂下來，最值得加的其實只有三類：

1. 入口分流點
2. 訊息轉發點
3. 離線偵測點

入口分流點讓我知道：

- 收到了什麼 type
- 從哪個 client 來
- 要去哪個 room 或哪個 target

轉發點讓我知道：

- signal 有沒有找到對的目標
- room 與 to 是否一致

離線偵測點讓我知道：

- 是正常關閉、讀取錯誤、還是 deadline/ping 問題

只要這三個位置有資料，整個服務的主要事件流通常就能被還原出來。

這裡最重要的不是三這個數字，而是背後的思考方式：每一行 log 都要對應到一個判斷目的。當目的清楚，log 才不會變成噪音。

## log 的價值在於能把程式轉成事件時間線

後來我真的跑起服務，開兩個分頁測試同房 join/leave，看到像這樣的事件順序時，很多理解一下就落地了：

- 收到 join
- join 成功
- peer-joined 通知既有成員
- 收到 signal
- 轉發 signal
- read error
- unregister
- leave

這些訊息本身不複雜，但一旦照著時間排開，你就能把程式從一堆函式名稱，變成一段實際發生的故事。

這也是我覺得 log 最有價值的地方：它不是補充說明，而是把動態行為可視化。

對初學者來說，這一點特別重要。因為很多時候我們以為自己在學語法，實際上更缺的是一種能力：能不能把執行中的系統，讀成一段合理的事件故事。

## 一個很小的例子：room 為什麼一開始是空字串

我加 log 時，曾看到 join 進來時 `room` 顯示空字串，後來在 `handleJoin` 又變成正確的 `test`。

這種時候如果只是看表面，很容易懷疑是不是哪裡壞了。

但因為我有把入口與處理位置對起來，很快就理解：

- 入口時記到的是 client 目前狀態上的 `c.room`
- 那時 client 還沒真正被 `handleJoin` 指派進房間
- 真正的房間名稱在 join 訊息裡的 `msg.Room`

這個小例子很能說明一件事：

很多除錯，不是靠更多 log，而是靠更精準地知道每個值在那個時間點代表什麼。

這句話對我來說比任何除錯技巧都更重要。因為它提醒我，除錯不是資料蒐集競賽，而是語意判讀能力。

## 錯誤訊息本身也是教材

這次過程中，我也碰到過一個很典型的錯誤：

`listen tcp :3000: bind: address already in use`

這種錯誤如果只當成阻礙，其實很可惜。它本身就是很好的學習材料，因為它迫使你去理解：

- 服務是怎麼綁定埠號的
- 為什麼會有其他程序先占住這個 port
- 開發模式與正式模式如何使用不同埠號

也就是說，錯誤訊息不是只拿來解決問題，它還能幫你建立系統觀。

這也是我很想保留在系列裡的一種學習視角：不要把錯誤訊息只當障礙物，很多時候它其實就是教材本身。

## 讓 AI 參與除錯，和讓 AI 代替除錯，是兩件不同的事

我很喜歡這次互動裡的一點：AI 沒有直接叫我把一堆 log 全貼滿，而是先幫我縮小問題邊界。

例如它會先問：

- 你現在最想判斷的是 join 是否成功，還是 signal 是否送到
- 如果只能選一個位置加 log，哪裡最能區分這兩種可能

這種互動方式很像在訓練除錯思維，而不只是代勞。

對我來說，這也是 AI agent 在學習裡最有價值的角色：不是幫我跳過理解，而是幫我更快建立理解。

這種差別很重要。因為一旦你只是請 AI 代替你除錯，你最後可能解掉了一次問題，卻沒有建立下一次還能自己判讀的能力。

## 如果你也想這樣學，可以怎麼問 AI

碰到新語言服務端除錯時，我很推薦先問這幾題：

1. 如果只能加 3 個 log，你建議加哪裡
2. 哪一行 log 最能區分 join 問題與 signal 問題
3. 這個錯誤訊息代表的是語法錯、執行錯、還是環境錯
4. 哪些 log 屬於高雜訊，應該先刪掉

這些問題都會直接提升你讀懂系統的速度。

如果你想把這套方法變成習慣，我很推薦每次除錯時都多問一句：我現在加這一行 log，是想排除哪個假設？只要這句話答不出來，通常就代表還不夠精準。
