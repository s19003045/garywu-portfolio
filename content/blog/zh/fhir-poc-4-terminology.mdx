> **這篇適合誰**：所有人——這是整個系列我最有資格寫的一篇。技術讀者會學到 FHIR 術語系統的機制；非技術讀者（包括 HR）會看懂一件事：為什麼「懂檢驗又懂軟體」在這個領域是稀缺組合。

## 你早就懂術語系統，只是當年它叫「檢驗項目對照」

每家醫院的 LIS 都有自己的檢驗項目碼。我們家的空腹血糖叫 `GLU-AC`，隔壁醫院叫 `009002`，儀器輸出又是另一套。院內溝通沒問題——一出院門就是災難：健保申報要對照、跨院轉檢要對照、換一台儀器要重新對照。

我在檢驗科的 14 年裡，這種對照表修過無數次。當時不知道的是：這個問題有一個國際級的正式解法，而它是 FHIR 語意互通的地基。

## system + code：語意的全球座標

FHIR 規定，代碼永遠是三件事的組合：

```json
{
  "system": "http://loinc.org",    // 哪一套代碼系統（命名空間）
  "code": "1558-6",                // 在那套系統裡的代碼
  "display": "Fasting glucose [Mass/volume] in Serum or Plasma"
}
```

`code` 沒有 `system` 就沒有意義——`04` 在健保科別表是兒科，在別的表可能是別的東西。**system + code 才構成一個全球唯一的「語意座標」**：`http://loinc.org|1558-6` 在世界任何角落都是空腹血糖，不多不少。

本 POC 的術語對應表涵蓋了六個領域，每一行都模擬真實導入專案的「對照工作底稿」：

| 領域 | 院內表示法 | 標準代碼系統 | 例子 |
|---|---|---|---|
| 檢驗項目 | `GLU-AC` | **LOINC** | `1558-6` |
| 檢驗單位 | 自由文字 | **UCUM** | `mg/dL`、`10*3/uL` |
| 生命徵象 | 欄位名 `sbp`/`dbp` | **LOINC** | `8480-6` / `8462-4` |
| 診斷 | ICD-10-CM | ICD-10-CM 2023（TW Core 版） | `E11.9` |
| 藥品 | 健保藥品代碼 | **ATC** | `A10BA02`（metformin） |
| 科別 | 健保科別碼 | **SNOMED CT** | `419192003`（內科） |

連「單位」都是代碼：白血球的 `10^3/µL`，每家醫院寫法都不同（`K/uL`、`x10E3/uL`……），UCUM 的標準寫法是 `10*3/uL`。POC 的做法是雙軌並存——`unit` 欄位保留院內習慣寫法給人看，`code` 欄位放 UCUM 給機器比對。

## 一個真實教訓：查表，不要憑印象

POC 開發中踩過一個典型的坑。我們把健保科別碼 `04`（兒科）直接放進就診資源的科別欄位，TW Core 驗證器回了 error：這個欄位綁定的值集，只收「**無法對應到 SNOMED CT**」的特殊科別——常見科別因為對應得到，反而必須用 SNOMED 表達。

解法不是用猜的。TW Core IG 的 package 裡就附了官方對照表（ConceptMap），直接查：

```
01 家醫科 → 419772000 Family practice
02 內科   → 419192003 Internal medicine
04 兒科   → 24251000087109 General pediatric specialty
```

注意兒科的答案：`24251000087109`——不是多數熟悉 SNOMED 的人會直覺猜的 `394537008`。**術語對應永遠查官方對照表，不憑印象**。這條紀律在檢驗室有一個完全同構的版本：發報告前對照 SOP，不背數值。

## 為什麼這是「人力黑洞」，以及為什麼需要雙背景的人

本 POC 對應了 10 個檢驗項目、6 種藥、5 個科別。真實醫院是**上千個檢驗項目、上萬筆藥品檔**，而且：

- 有些院內項目對不到單一 LOINC——一個院內「套餐」可能等於多個 LOINC 項目
- 有些老項目連現任負責人都不確定當年的定義，要翻 SOP、問資深醫檢師
- 對應需要臨床專業審核——**工程師看不出 `GLU-AC` 和 `GLU-PC`（空腹與飯後血糖）的差別，醫檢師一眼就看出來，而且知道搞混的臨床後果**

最後一點就是我寫這篇文章真正想說的事。術語對應是 FHIR 導入專案中最無法壓縮工期的環節，而它卡住的原因從來不是技術——是**翻譯**：把臨床語言翻成工程語言，再翻回去。市場上會寫 ETL 的工程師很多，看得懂檢驗項目定義的醫檢師也很多，**同一個人同時會這兩件事的，非常少**。

## 工程上的正解：對照表本身也是 FHIR 資源

最後一個機制之美：FHIR 把術語本身也做成資源——`CodeSystem`（字典）、`ValueSet`（欄位允許值的圈選）、`ConceptMap`（字典間的對照）。這意味著對照表不必散落在 Excel 或寫死在程式裡：存進 FHIR server 之後，版本控制、改動稽核、權限管控、查詢 API（`$translate`：丟院內碼、回標準碼）全部免費獲得。

**用管資料的同一套基礎設施管理「對資料的詮釋」**——這是 FHIR 設計裡我最欣賞的一筆。

> **決策者視角**：評估 FHIR 專案時程時，把「術語對應」單獨列項並配置臨床人力（檢驗、藥劑、病歷）。它決定專案成敗的程度，大於所有純技術項目的總和。而能主持這件事的雙背景人才，是值得專門去找、去養的。
