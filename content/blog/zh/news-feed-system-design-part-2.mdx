> 這是「動態消息系統設計」系列的第二篇。建議先讀 [Part 1](/zh/blog/news-feed-system-design-part-1)——我們在那篇從一句崩潰的 SQL，一路推導到「普通人推、名人拉」的混合架構。這篇接著補上三個刻意留下的洞：信箱住哪、投遞怎麼不卡住使用者、失敗了誰補救。

## 接續上一篇：我們還欠三個答案

快速回顧一下 Part 1 走到哪。我們設計的是一個首頁時間軸（你打開 App 看到的、你追蹤的人的最新貼文）。最直覺的「讀的時候現場撈 200 人的貼文來排序」會在規模下崩潰，所以我們把昂貴的工搬到發文那一刻：**A 發文時，就先把貼文投遞進每個粉絲的「信箱」**；B 看首頁時，直接拿自己的信箱就好。名人粉絲太多會塞爆，所以名人改成「不投遞、讀的時候才現場撈」。

聽起來很完整，但我當時其實講得很心虛，因為有三個問題我還答不出來：

1. 這個「信箱」到底**存在哪裡**？用什麼東西裝，才能讓「投遞」「取最新 20 筆」「丟掉太舊的」都很快？
2. 普通人發一則文要投遞 5000 個信箱。如果這 5000 次投遞要**使用者站在那裡等完**，他不也卡住了嗎？
3. 萬一投遞到一半**失敗**了，誰來補救？怎麼保證貼文「就算晚一點，最終一定送到」？

這一篇就是把這三個洞補起來。而補洞的過程，會自然逼出兩個你常聽到、但可能沒真的搞懂的東西：**Redis** 和 **Kafka**。

## 信箱該住在哪：先問「掉了會怎樣」

我以前對「存資料」的理解很單純：資料就是存進資料庫，存完就安全了。後來我才學到一個更重要的分類問題，它會決定一份資料該放在哪裡——

> **這份資料如果整個掉了，會怎樣？**
>
> - 如果掉了就**永遠回不來、會出大事**——那它是你的「真相來源」，必須好好存在可靠、持久的地方（像傳統資料庫）。
> - 如果掉了**還能重新算出來、只是麻煩一點**——那它只是一份「快取」，可以放在比較快、但比較不耐久的地方。

拿我們的東西來套：

- **貼文本體、追蹤關係**：這是真相來源。貼文沒了就是沒了，沒人能憑空生回來。→ 放可靠的資料庫。
- **信箱（每個人首頁那疊貼文）**：它其實是**可以重算的**。如果某個人的信箱整個掉了，我們大不了回去翻「他追蹤誰、那些人最近發了什麼」，重新投遞一次就好。慢，但不會永久遺失任何東西。→ 它只是快取。

那「比較快」的地方是什麼？這裡就輪到 **Redis** 登場。

簡單講，**Redis 是一個把資料放在「記憶體」裡的資料庫**。一般資料庫把資料寫在硬碟上（耐久、便宜、但慢）；Redis 把資料放在記憶體裡（超快，但記憶體比較貴，而且機器一重開，沒特別處理的話資料就沒了）。

所以 Redis 跟「信箱」是天作之合：信箱被讀得超級頻繁（每秒幾十萬次），需要快——Redis 快；信箱掉了能重算、不致命——Redis 那個「不太耐久」的缺點，剛好我們不在乎。**選對工具，不是選最強的，是選缺點剛好你不在乎的那個。**

## 用什麼裝？一個會「自動排序」的資料結構

信箱住進 Redis 了，但還有個問題：用 Redis 裡的**什麼結構**來裝這疊貼文？

你可能會想：不就是一個清單（陣列）嗎，一則一則排好放進去就好。可以，但你看看信箱要做哪些事：

- 投遞時，要把新貼文插進「對的時間位置」。
- 看首頁時，要拿「最新的 20 筆」。
- 信箱不能無限長，要能「丟掉太舊的」。

普通清單做這些事都得自己手動維護順序，很麻煩。Redis 剛好有一種結構天生就是為這個設計的，叫 **Sorted Set（有序集合）**。

它的特別之處：**裡面每一個項目，都綁著一個「分數」，Redis 會自動依分數幫你排好。** 你完全不用自己排序。

那分數用什麼？答案很自然——**用「發文的時間」當分數**。時間越新、分數越大，Sorted Set 就自動把它排在越前面。於是信箱永遠是依時間排好的，不費你任何力氣。

如果你想看實際的 Redis 指令長怎樣（看不懂可以略過，看後面的白話就好）：

```bash
# 投遞一則貼文進 B 的信箱（分數用發文時間）
ZADD feed:user_B 1042 post_987

# 看首頁：拿最新的 20 筆
ZREVRANGE feed:user_B 0 19

# 控制長度：只保留最新 1000 筆，舊的砍掉
ZREMRANGEBYRANK feed:user_B 0 -1001
```

### 順帶一個重要決定：信箱裡只放「編號」，不放「整篇貼文」

你可能注意到上面信箱裡放的是「貼文 #987」這種**編號**，而不是貼文的完整內容。這是個刻意的決定，而且很關鍵。

想像一下：如果信箱裡放的是貼文的完整內容，那一位名人發一則長文，這篇文就會被**完整複製**到他幾千萬個粉絲的信箱裡——同一篇文存了幾千萬份，儲存空間直接爆炸，而且哪天要改一個字，得改幾千萬個地方。

所以正確做法是：**信箱裡只放貼文的編號（很輕），貼文的完整內容另外存一份、大家共用。** 看首頁時，先從信箱拿到 20 個編號，再拿這 20 個編號去把內容撈出來。這就像圖書館的**索引卡**——卡片上只寫書名和編號，真正的書只有一本放在書架上，所有人共用那一本，而不是每張卡片都附一本完整的書。

> 這裡藏著一個會反覆出現的原則：**凡是會被很多人重複用到的東西，就抽出來存一份、大家共享，絕不複製。** 記住它，後面還會用到。

## 第二個洞：投遞 5000 個信箱，憑什麼要使用者乾等？

信箱的事解決了，回到第二個洞。

普通人發一則文，要投遞進 5000 個粉絲的信箱。如果我們的流程是「使用者按下發送 → 系統老老實實投遞完這 5000 個信箱 → 才回他『發送成功』」，那這個人就得**站在那裡等這 5000 次投遞跑完**。5000 個還好，但如果是個有點人氣、十幾萬粉絲的帳號呢？他會等到不耐煩。

問題出在哪？出在我們把兩件本來可以分開的事**綁在一起**了：

- 「**把貼文安全收下**」——這件事使用者很在乎，要快。
- 「**推送給每一個粉絲**」——這件事使用者其實不在乎細節，他只希望「最終會送到」就好，晚個幾秒沒關係。

既然第二件事使用者不在乎要等，那我們為什麼要讓他等？**把它丟到背景去慢慢做，使用者按下發送就立刻放他走，不就好了？**

這個「不讓使用者等、丟到背景做」的做法，就叫**非同步（asynchronous）**。而要把工作可靠地丟到背景，我們需要一個專門的角色——這就是 **Kafka** 登場的地方。

## Kafka：一條不會弄丟東西的輸送帶

先別管 Kafka 這個名字，先想我們需要一個什麼樣的東西：

我們需要一個地方，讓使用者發文時可以「把一張**待投遞的工單**丟進去就走人」，而這個地方要**保證這張工單不會弄丟**，後面再有一排工人慢慢把工單拿下來、實際去投遞信箱。

Kafka 就是這個東西。你可以把它想成一條**可靠的輸送帶**，或一張**永遠不會弄丟的待辦清單**：

- 你把工單放上輸送帶，它一定幫你保管好（工單會被寫到硬碟、還會複製好幾份，不怕單一台機器壞掉）。
- 輸送帶後面站著一排**工人（worker）**，從帶子上一張一張拿工單下來處理（實際去投遞那 5000 個信箱）。

有了這條輸送帶，新流程變成：使用者按下發送 → App 伺服器只做兩件最低限度的事（把貼文本體存好、把一張「請投遞 post_987」的工單丟上 Kafka）→ **立刻回他「成功」**。此刻那 5000 個信箱一個都還沒投遞，但使用者已經走了。背景的工人再不慌不忙地把工單拿下來、慢慢投遞。

這條輸送帶順手幫我們解決了三件事，每一件都很實用：

- **不用乾等（解耦）**：發文者丟完工單就走，不必等投遞完成。
- **尖峰不爆（緩衝）**：跨年夜大家瘋狂發文時，工單先堆在輸送帶上，工人用自己穩定的速度慢慢消化，不會被瞬間的暴量打垮。輸送帶像個蓄水的水庫。
- **不怕失敗（重試）**：工單一旦上了帶子就被妥善保存。工人處理到一半掛掉了，工單還在，換個工人重做就行——東西不會憑空消失。

## 那「發送成功」到底保證了什麼？

這裡有個很細、但面試官超愛追、實務上也真的重要的問題：

使用者收到「成功」的那一刻，他的貼文其實**還沒進任何一個粉絲的信箱**（工人才正要開始投遞）。那這句「成功」到底在保證什麼？如果就在「回了成功、但工人還沒動工」的那一瞬間，整個系統掛了，這則貼文會不會消失？

答案是不會，而關鍵就在前面那句「App 伺服器只做兩件事」：**把貼文本體存好、把工單放上 Kafka。** 只要這兩件事都確實落地了（貼文存進了可靠的資料庫、工單寫進了會保存到硬碟的 Kafka），那麼就算 App 伺服器下一毫秒爆炸、工人全部罷工，這則貼文和那張工單都還好端端地躺在那裡，系統恢復後，工人接著把它投遞完就好。

所以「發送成功」這句話的精確意思是：

> **「你的貼文已經被安全收下，而且一定會送達粉絲」**——而不是「已經送達粉絲」。

這個區分就是非同步系統的「承諾邊界」。而它之所以成立，靠的是我們在 Part 1 一開始就定下的一條規格：**新貼文「最終一定看得到」就好，晚幾秒沒關係。** 正因為使用者能接受「最終送到」而不是「立刻送到」，我們才有資格把投遞推到背景。一個概念的伏筆，在這裡兌現了。

## 重試的陷阱，與一個你天天在用的性質

前面說「工人掛了就重試」。但「重試」會帶來一個新危險，這也是面試愛追的點：

假設一個工人正在投遞某則貼文，投到第 3000 個信箱時掛了。工單還在輸送帶上，於是換另一個工人從頭再投一次。那……前面那 3000 個**已經投過**的信箱會怎樣？同一則貼文，會不會在某些粉絲的信箱裡出現**兩次**？

我們需要一個性質來保證「重做不會出錯」，這個性質叫 **冪等（idempotency）**。聽起來很玄，但它就是你天天在用的東西：

> 電梯的呼叫鈕，你按一次和按五次，電梯就是來一次。多按沒有任何副作用。這就是冪等——**同一個操作做一次和做很多次，結果完全一樣。**

那我們的投遞怎麼做到冪等？其實上一節的設計已經幫我們鋪好路了。還記得信箱（Sorted Set）裡，每一格的身分是用**貼文編號**嗎？同一個貼文編號投遞第二次，Sorted Set **不會多生出一格**，只會蓋在原本那一格上。所以重投是安全的，貼文不會變兩筆。

但這裡有一個我自己一開始沒注意到的小陷阱：重投時蓋上去的「分數」，必須跟原本一樣。如果工人重試時，圖方便用「現在這一刻的時間」當分數，而不是用「貼文原本的發文時間」，那第二次投遞就會把這則貼文的時間**改掉**，它在粉絲首頁裡的位置就會莫名其妙地跳動。

所以正確的冪等，不是憑空得來的，而是靠**用穩定的、屬於貼文本身的東西當鑰匙**：拿「貼文編號」當每一格的身分、拿「貼文的發文時間」（而不是投遞當下的時間）當分數。只要這兩個都來自貼文本身，同一則貼文投幾次，結果都一模一樣。

這個冪等的觀念其實到處都是。我之前在別的場景也踩過同一個坑——一個動作可能被重複觸發時，你就得想辦法讓「重複」不造成傷害。很多看起來不同的問題，骨子裡是同一個。

## 別忘了名人：他不走這條輸送帶

最後收個尾。我們前面聊的整條「丟工單 → 工人投遞信箱」的非同步路徑，是給**普通人**用的。名人呢？

回想 Part 1：名人發文是**不投遞信箱**的。所以名人發文時，這條輸送帶根本不該啟動——如果照普通人那樣，把名人的投遞工單也丟上去，那一位上億粉絲的名人一發文，就往輸送帶上灌上億張工單，瞬間把工人全部壓垮。這跟 Part 1 那個「塞爆信箱」的災難是同一隻怪（hot key），只是這次它壓垮的是工人。

所以 Part 1 那條「用粉絲數分流」的邏輯，其實一路貫穿到了這裡：**普通人才走 Kafka 投遞，名人根本不進 Kafka，只更新自己的貼文，等粉絲上線時現場撈。** 分流不是只發生在「要不要投遞信箱」，而是延伸到「要不要上輸送帶」。

## 我們現在站在哪

把這兩篇連起來看，整個寫入的故事已經完整了：

使用者發文 → 系統存好貼文、看粉絲數分流。**普通人**：丟一張投遞工單上 Kafka，立刻回「成功」，背景工人冪等地把貼文投進每個信箱（用 Redis 的 Sorted Set 裝、發文時間當分數、只放編號不放內容）。**名人**：只更新自己的貼文，不投遞。**看首頁**時，再把信箱和名人的貼文合併排序。

我們現在有一個跑得順、扛得住、又不卡使用者的設計了。但工程裡有句話：**真正考驗一個系統的，不是它一切正常的時候，而是東西開始壞掉的時候。**

下一篇 Part 3，我們就來故意搞破壞：如果背景工人的速度跟不上、工單越積越多怎麼辦？如果裝著幾億人信箱的 Redis 整個掛掉，會發生什麼——而且為什麼這可能引發一場「雪崩」，連帶把資料庫也拖垮？以及那隻叫 hot key 的怪，會在這個系統裡第三次現身。把這些壞掉的場景都想過一遍，這個設計才算真的完整。
