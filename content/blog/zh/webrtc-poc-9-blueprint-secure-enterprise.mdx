[上一篇](/zh/blog/webrtc-poc-8-blueprint-meet-like-platform)寫了「開放大型平台」的完整藍圖。這篇換到光譜的另一端：**資安嚴謹的跨國大廠**——嚴格到員工禁帶個人 3C 進公司。人數不一定多，但每一個決定都被「資料不能外流」與「要符合多國法規」綁住。

你會看到：同樣是「互動型視訊」，跟 Meet 類用一樣的媒體模型（SFU），但因為合規這條軸，幾乎每個選擇都被推往相反方向。

> 一樣是「若目標是這個場景，我會這樣做」的規劃，不是實作報告。

## 1. 場景與硬限制

- **規模形狀**：很多中小型會議（場景 A），但**極度敏感**。
- **資料主權**：媒體、錄影、log **絕不能離開公司可控環境**；跨多國時，各國資料可能要分區落地。
- **裝置管控**：禁帶個人 3C → 只能用**公司配發或受管裝置**（受控瀏覽器或桌面 App + MDM）。
- **網路**：在嚴格企業防火牆內，常封 UDP、只放行 443。
- **身分**：綁公司目錄，不可能用 Google 之類的消費級登入。
- **不可妥協**：地端／私有雲、完整稽核、E2EE 選項、能穿透嚴格防火牆、可通過稽核。

這些限制比「規模」更主導架構。

## 2. 參考架構（全部在公司可控環境內）

```
  受管裝置/受控瀏覽器
        │  SAML/OIDC
        ▼
  ┌──────────────┐  會議/權限/稽核   ┌──────────────┐
  │ 企業 IdP     │   ┌────────────┐  │ Postgres(地端)│
  │ (AzureAD/    │──▶│ Auth/API   │──┤ 稽核 log → SIEM│
  │  Okta/LDAP)  │   │ (地端)      │  └──────────────┘
  └──────────────┘   └─────┬──────┘
                           │ 短效 token(含部門/權限)
                           ▼
  ┌───────────────────────────────┐
  │ LiveKit 自架(地端 k8s)         │── 錄影 → 地端儲存(嚴格存取 + 法務保留)
  └───────────────┬───────────────┘
                  │ UDP 被封時
                  ▼
        coturn(TURN over TLS 443)
```

關鍵：**沒有任何一條線連到外部公有雲 SaaS**。所有元件都在公司可控的機房／私有雲內。

## 3. 媒體層（深）

媒體模型仍是 SFU（互動型），但**必須地端自建**——因為公有雲 SaaS 等於把媒體交給外部，直接違反「資料不外流」。

- **LiveKit 自架於地端 k8s**：拿到開源 SFU 的能力，又把資料留在公司內。這正是 Phase 6 自建經驗最能兌現的場景——你知道怎麼營運它、怎麼除錯它。
- **嚴格防火牆穿透**：企業網常封 UDP。對策：**coturn + TURN over TLS（443 埠）**，讓媒體能偽裝成一般 HTTPS 流量穿出去。沿用 Phase 6 的 `UDP_PORT` 固定埠 + `NAT1TO1_IP` 概念，但再加 TLS relay 後援。
- **可選：強制 relay**：基於安全，可關閉 P2P 直連、一律走 TURN，避免暴露內部 IP 拓樸。
- **容量**：跑在自有硬體上，依機房容量估算；simulcast 仍有用，但人數通常不是瓶頸，合規與穩定才是。

## 4. 身分與存取（深）

- **登入：企業 SSO**，串公司既有 IdP（Azure AD / Okta / 自架 LDAP），協定用 **SAML 2.0 或 OIDC**；用 **SCIM** 自動同步帳號與離職停權。
- **角色來自目錄**：部門、職級、群組直接從 IdP 對應到會議權限，不另建一套帳號。
- **外部訪客**：預設禁止；若必要，走嚴格受控流程（額外驗證 + 時效 + 浮水印 + 受限能力）。
- **token claims**：除了 room/role，還夾帶部門、密級、甚至**裝置認證結果**（只有 MDM 受管裝置才放行）。
- **會議與目錄綁定**：會議掛在組織單位下，ACL 依目錄群組。

## 5. 資料與合規（此場景的重心）

- **資料落地**：依各國法規，媒體與錄影分區儲存在對應地區的地端機房。
- **E2EE**：法規要求「連伺服器都不能看內容」時，用 insertable streams 做端對端加密。**取捨**：SFU 看不到媒體 → 伺服器端錄影／字幕失效，需改用受控的金鑰託管或客戶端錄影來滿足「合規錄影」需求。
- **稽核**：誰、何時、加入哪個會議、做了什麼，全部寫**不可竄改的稽核 log**，串接 SIEM，可供法務調閱與法律保留（legal hold）。
- **保留與刪除**：明確的保留期與到期銷毀政策。

## 6. 前端 / UX（鎖得更緊）

- **受控用戶端**：受管桌面 App 或受控瀏覽器；停用個人錄影、限制檔案分享（或經 DLP 掃描）。
- **防外洩**：畫面**浮水印**（嵌入使用者 ID，截圖外流可溯源）、螢幕分享控管。
- **體驗讓位給安全**：很多 Meet 類的便利功能（隨手分享連結、訪客一鍵進）在這裡會被刻意關掉。

## 7. 可觀測性、維運與成本

- **稽核級記錄 + SIEM**：不只看系統健康，還要看「政策違規」告警。
- **維運即最大成本**：地端基礎設施的部署、修補、災備、以及通過各種合規認證（如 ISO 27001、各國資料保護）的長期投入。
- **指標**：節點 + 逐連線品質照樣要，但更在意「連得上嗎」（嚴格 NAT 穿透成功率）。

## 8. 主要風險與失效模式

| 風險 | 失效樣子 | 緩解 |
|---|---|---|
| 內部資料外洩 | 員工側錄/截圖外流 | 浮水印、DLP、停用個人錄影、稽核溯源 |
| 嚴格防火牆連不上 | UDP 全封、會議建不起來 | TURN over TLS(443)、強制 relay 後援 |
| 稽核不過 | 缺 log、無法溯源 | 不可竄改稽核 log + SIEM + 保留政策 |
| E2EE 金鑰管理 | 金鑰外洩或遺失 | HSM/KMS 管理、嚴格存取控制 |
| 跨國法規衝突 | 資料放錯地區 | 各國資料分區落地 + 區域路由 |

## 9. 技術棧速覽

- **用戶端**：受管桌面 App / 受控瀏覽器（搭配 MDM）。
- **身分**：企業 IdP（SAML/OIDC）+ SCIM。
- **Auth/API**：地端自建，簽夾帶權限/裝置認證的短效 token。
- **媒體**：LiveKit 自架於地端 k8s。
- **NAT**：coturn（TURN over TLS 443、可強制 relay）。
- **狀態/儲存**：地端 Postgres、各國分區的地端物件儲存。
- **安全/稽核**：SIEM、HSM/KMS（E2EE 金鑰）、DLP。

---

對照上一篇就會發現：媒體模型一樣（SFU），但「能不能用公有雲、用什麼登入、要不要 E2EE、體驗讓不讓位給安全」全都相反。**這就是「同一套軸、不同目標、不同答案」最戲劇化的一組對照。** 下一篇是最後一個場景，也是形狀完全不同的——萬人演唱會直播。

## 名詞小抄

- **SSO / IdP**：單一登入 / 身分提供者（企業常用 Azure AD、Okta、LDAP）。
- **SCIM**：跨系統的帳號自動佈建與停權標準。
- **E2EE / insertable streams**：端對端加密；瀏覽器讓你在送出前加密媒體的機制。
- **TURN over TLS**：把媒體中繼包進 TLS（443），穿透只放行 HTTPS 的防火牆。
- **SIEM**：彙整與分析安全事件的系統，供稽核與告警。
