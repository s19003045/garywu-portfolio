前面幾個 phase 做完後，一件事已經很清楚：mesh 可以幫助理解 WebRTC，但它不是多人視訊系統的終點。

真正要走向更多人、更穩定的房間，架構必須從 mesh 轉成 SFU。

Phase 5 和 Phase 6 處理的，就是這個轉折。

這篇先記一件事：真正的規模化不是把 server 開大，而是把媒體轉發、路由、共享狀態和觀測一起改好。

## 先用白話理解

SFU 的重點不是「中間多一台 server」，而是讓每個人只需要上傳一路影像，再由 server 幫忙轉發給其他人。

如果 mesh 像是每個人都自己打給所有人，SFU 就像由中繼站幫你把同一份訊號送到不同收件者。

## SFU 改變的是頻寬模型

在 mesh 裡，每個人要把自己的影像上傳給房間內其他每個人。

SFU 的模型不同。每個 client 只上傳一路媒體到 server，再由 server 轉發給其他人。

這個改變看起來只是「中間多了一台 server」，但本質上是把上傳成本從 O(N) 降到接近 O(1)。

對使用者端來說，這是非常關鍵的差異。因為大多數使用者的上傳頻寬遠比下載頻寬有限，mesh 的瓶頸通常會先卡在 client 端。

## 自建 SFU 的目的不是取代成熟產品

Phase 5 用 Go + Pion 建了一個最小 SFU。

這不是因為正式產品一定要自己寫 SFU。相反地，如果目標是快速做出可商用的大型視訊系統，LiveKit 這類成熟方案很值得評估。

但在學習與架構理解上，自建一個最小 SFU 很有價值。

因為你會真的碰到：

- server 也要參與 WebRTC negotiation
- server 要接收 client 上傳的 track
- server 要把 track 轉發給其他訂閱者
- 有人加入或離開時，可能需要重新協商
- simulcast 會影響不同網路條件下的畫質選擇

這些問題如果完全交給框架包掉，很容易只知道「它可以用」，但不知道系統出問題時該往哪裡查。

## 單節點 SFU 還不是規模化

做到 SFU 之後，單房人數上限會比 mesh 好很多。

但這還不是數千人系統。

因為單節點仍然會有 CPU、記憶體、頻寬與連線數上限。當房間變多、使用者變多，下一個問題會變成：使用者應該被導到哪一個 SFU？同一個房間的人是否在同一個節點？節點掛掉時狀態如何恢復？

這也是 Phase 6 要補上的東西。

## Router、Redis、JWT 與 Prometheus 不是裝飾

Phase 6 加入多 SFU 節點、Router、Redis、JWT、Prometheus 與壓測。

這些看起來像營運配備，但其實每一個都對應到實際限制。

Router 解決房間要被分配到哪個 SFU 節點的問題。

Redis 解決多節點之間共享房間與節點狀態的問題。

JWT 解決使用者是否有權加入房間的問題。

Prometheus 解決系統出問題時是否看得見的問題。

壓測則是避免只靠想像判斷架構是否能承受負載。

也就是說，Phase 6 開始處理的不只是「通話能不能成立」，而是「這個系統是否能被營運」。

## 真正的轉折

回頭看整個專案，Phase 5 是架構上的轉折，Phase 6 是系統化上的轉折。

Phase 5 讓媒體模型從 peer-to-peer 轉成 server-assisted forwarding。

Phase 6 讓單一服務變成可以被路由、監控、壓測與擴展的系統。

這兩件事加起來，才比較接近正式視訊產品會面對的問題。

## 這個系列最後想說的事

如果只看最終結果，這個專案好像是在做一個 WebRTC 視訊系統。

但對我來說，它更像是一個架構演進練習。

每個 phase 都不是隨機加功能，而是在回答一個具體問題：

- 1:1 通話需要哪些最小協調？
- Firestore 能不能取代 signaling server？
- mesh 的上限在哪裡？
- 前後端如何變得可維護？
- SFU 為什麼是多人視訊的關鍵？
- 多節點之後，營運問題會如何浮現？

真正有價值的，不只是最後跑起來的程式，而是這些限制被逐一看見、拆解與記錄下來。

這也是我覺得這個專案適合寫成系列文章的原因：它不是一次完成的展示品，而是一段把問題慢慢逼出來的工程過程。

## 名詞小抄

- **SFU**：Selective Forwarding Unit，負責接收並轉發媒體的伺服器。
- **Simulcast**：同一路影像同時送出多種畫質。
- **Router**：決定使用者該被導到哪個 SFU 節點的元件。
- **Redis**：多節點共享狀態時常用的記憶體資料庫。
- **Prometheus**：蒐集與觀察系統指標的監控工具。
