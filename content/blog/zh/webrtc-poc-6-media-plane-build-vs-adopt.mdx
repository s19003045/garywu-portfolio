[上一篇](/zh/blog/webrtc-poc-5-production-ready-depends-on-goals)立了一套「從目標反推策略」的思考方式，並丟出三個場景。這篇把焦點放在最花錢、也最難回頭改的決定：**媒體層怎麼選**。

媒體層就是「影像聲音實際怎麼流動」的那一層。它的選擇會牽動成本、延遲、可擴展性與合規，所以值得單獨想清楚。

## 三條路，各自解不同的問題

媒體層大致有三條路，不是互斥，常常會混用：

- **自建 SFU**：自己用 Go + Pion（或其他）維護一套轉發叢集。最大掌控、也最大維護負擔。
- **採用成熟方案**：LiveKit（自架或雲端）、或 Daily / Agora / Twilio 這類 SaaS。用上線速度換掉維運。
- **廣播管線**：把媒體轉成 HLS / LL-HLS，交給 CDN 分發。用幾秒延遲，換近乎無限的觀眾規模。

關鍵問題是：**你的場景是「互動」還是「廣播」，以及資料能不能放到別人的雲上。** 這兩題會把你導向不同的路。

## 互動型：自建 vs 採用

如果大家都要開鏡頭即時互動（Meet 類、企業會議），媒體模型就是 SFU。問題只剩「自己維護，還是用別人的」。

自建到 Phase 6 之後，我很清楚自建長期要扛什麼，這些**框架都會幫你包掉**：

- simulcast / SVC：同一路影像送多種畫質，讓接收端依網路挑 layer。
- TURN 叢集：嚴格 NAT / 企業防火牆下，純 STUN 連不上時的中繼。
- 自動擴縮 + graceful drain：節點隨負載增減，下線時不能硬斷現有通話。
- SFU 串接（cascading）：超大房需要多節點接力轉發。
- 容錯、跨區、頻寬估測、錄影……

每一項都不小。所以對「要快、要省心」的互動型產品，我的傾向很明確：**採用 LiveKit（它基於 Pion，跟我自建的心智模型幾乎一致），把工程力留給應用層。**

那自建那段就白做了嗎？完全不是。下面會講它幫我帶走什麼。

## 廣播型：萬人演唱會不該都塞 WebRTC

萬人演唱會直播是另一種世界。如果硬把一萬個觀眾都接成 WebRTC，單一房間的下載總量接近 O(N²)，任何 SFU 都會被壓垮。

但仔細看這個場景：**真正在「發送」的只有舞台上少數人，其餘上萬人都是「觀看」。** 那就該分層：

- 少數發布者：用 WebRTC / SFU 進來（甚至先匯流成一路節目訊號）。
- 海量觀看者：改走 **LL-HLS 之類的串流 + CDN**。觀眾用 HTTP 拉流，CDN 邊緣節點可水平擴展到任意規模。

代價是延遲從「毫秒級」變成「數秒級」。但對純觀看的演唱會，幾秒延遲完全可接受，換來的是「成本和觀眾規模脫鉤」——這正是 CDN 擅長的事。

換句話說，這個場景的正解，根本不是「把 SFU 調得更強」，而是「**辨認出大多數人不需要互動，於是換一條完全不同的管線**」。

## 三個場景的媒體層落點

| 場景 | 媒體層選擇 | 為什麼 |
|---|---|---|
| 開放大型（Meet 類） | **採用 LiveKit**（雲端或自架皆可） | 互動型、要快、規模靠多房分散；自己維護不划算 |
| 資安嚴謹大廠 | **LiveKit 地端自架 + 自架 coturn** | 互動型，但**資料不能出公司**→ 不能用公有雲 SaaS；嚴格防火牆要 TURN |
| 萬人演唱會 | **少數發布者 SFU + 廣播 LL-HLS/CDN** | 廣播型；用延遲換無限觀眾，成本壓在 CDN 流量 |

注意「Meet 類」和「資安大廠」媒體模型一樣（都 SFU），但因為**合規**這條軸，一個可以用雲、一個必須地端——這就是上一篇說的「同一套軸、不同答案」。

## 從 Phase 6 帶走什麼

就算最後採用 LiveKit，自建那段也不是繞遠路。它讓我能**看懂、會除錯**一個原本是黑盒子的系統：

- 知道「伺服器也要參與 WebRTC 協商」「track 怎麼被轉發」「重新協商何時發生」——所以 LiveKit 出問題時，我知道往哪查。
- 懂「房間 token、房間親和性路由、per-peer 品質指標」這些概念——所以我看得懂 LiveKit 的設定與監控在說什麼。
- 知道 simulcast、TURN、cascading 各自在解什麼——所以我評估方案時不會被行銷話術牽著走。

**採用一個你「懂原理」的方案，跟採用一個你「只會照文件貼」的方案，是兩種不同的工程實力。** 自建的價值，就在這裡兌現。

## 名詞小抄

- **LL-HLS**：Low-Latency HLS，把延遲壓到數秒的 HLS 變體，適合大規模直播。
- **CDN**：內容傳遞網路，靠遍布各地的邊緣節點分發串流，觀眾規模幾乎不受單機限制。
- **simulcast**：同一路影像同時送多種畫質，讓接收端依網路條件挑選。
- **TURN / coturn**：嚴格 NAT 下的媒體中繼；coturn 是常見的開源 TURN 伺服器。
- **cascading**：SFU 節點之間接力轉發，用於單一超大房間。
