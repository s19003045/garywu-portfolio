## 一個血糖值的旅程

在成為軟體工程師之前，我在醫院檢驗科做了 14 年醫檢師。

一位病人抽血，生化分析儀跑出血糖 135 mg/dL。這個數值會經過：儀器 → LIS（檢驗資訊系統）→ 醫檢師審核簽發 → HIS（醫院資訊系統）→ 醫師的門診畫面。在一家醫院之內，這條路是通的。

但當這位病人下週去另一家醫院看診，對方的醫師想看這個血糖值時，問題來了：

- 兩家醫院的 HIS 是不同廠商、不同年代、不同語言寫的系統
- 我們家這筆資料叫 `GLU-AC`，對方家叫 `009002`——各自的院內代碼
- 就算檔案傳得過去，對方系統也不知道 `GLU-AC` 是什麼、單位一不一樣、參考區間為何

於是病人重抽一次血。時間、成本、病人的手臂，都在為「系統不互通」買單。

這件事我在檢驗科看了 14 年。轉職成為工程師後，我發現自己剛好站在能解決它的位置上——於是有了這個 POC，和這個系列。

## 問題的兩個層次

醫療資料交換難，難在它是兩層問題疊在一起：

1. **語法互通**：資料格式讀得懂——欄位怎麼切、編碼是什麼
2. **語意互通**：資料意義一致——「血糖」對兩邊系統來說是同一件事

傳過去但看不懂，和根本傳不過去，是同一種失敗。

**FHIR**（Fast Healthcare Interoperability Resources，唸作 "fire"）是 HL7 組織在 2014 年後推出的標準，它同時處理這兩層：用「資源（Resource）+ RESTful API」解決語法層，用「術語系統 + Profile」解決語意層。台灣衛福部在此之上發布了 **TW Core IG**（台灣核心實作指引），2025 年底推出 1.0.0 正式版——它正在成為台灣醫療院所交換資料的入場券。

## 這個 POC 證明了什麼

我用五個階段，把整條鏈打穿了一次：

```
模擬 HIS（SQLite，刻意保留台灣 HIS 的真實慣例：民國年、院內代碼）
   ↓  TypeScript ETL（術語對應、資料清洗、結構轉換）
FHIR Server（HAPI，Docker 一鍵啟動，自動載入 TW Core IG 1.0.0）
   ↓  標準 Search API
React 查詢介面（病人搜尋、檢驗報告、生命徵象、用藥）
```

可驗證的結果：608 筆 FHIR 資源上傳、**12 種 TW Core profile 通過機器驗證、0 error**、ETL 可重複執行不產生重複資料。「符合台灣規範」在這裡不是簡報上的宣稱，是 `$validate` API 判定的事實。

過程中真實踩過的坑——科別代碼要轉 SNOMED、機構代碼連假資料都不能編、SQLite 序號不重置導致的隱形 bug——全部保留在系列文章裡。**踩坑的過程比成功的結果更有教學價值。**

## 寫在前面的一句話

這個系列想證明的，除了技術可行性，還有一件事：**醫療資訊化最稀缺的不是工具，是能同時聽懂臨床語言和工程語言的人。** 工程師看不出 `GLU-AC` 和 `GLU-PC` 的差別，醫檢師看得出；醫檢師寫不出 ETL 管線，工程師寫得出。而這兩件事，可以是同一個人。

下一篇，我們從工程師最熟悉的地方開始：FHIR 到底是什麼。
