A historical-archive search system that had been in service for years (PHP 5.6 + MariaDB 10.4) needed to move to PHP 8.5 + MariaDB 11.8 for security compliance. I used the upgrade as the opportunity to deal with performance problems that had been accumulating just as long.

Results first — same k6 scripts, same thresholds, not a character changed between runs:

| Metric | Before | After | Change |
|---|---|---|---|
| Homepage p95 (50 VUs, mixed) | 23.99s (failing) | **76.92ms** | -99.7% |
| Map page p95 | 13.57s (failing) | **54.26ms** | -99.6% |
| Search overall p95 | 9.55s | **52.58ms** | -99.4% |
| Web container CPU peak | ~360% (saturated) | **~22%** | effectively idle |
| DB connection high-water mark | 101 | **7** | queue collapse gone |
| Mixed-scenario throughput | 3.96 req/s | **16.91 req/s** | +327% |
| Homepage browser requests | ~297 | **17** | -94% |
| Homepage finish time | 7.22s | **264ms** | -96% |

All four load tests at 50 concurrent users passed with zero HTTP errors. This article documents the whole process: how the bottleneck was diagnosed, how I decided what to change, which traps I hit — and one visual regression I caused myself and had to fix twice.

## Project Background

This is a textbook "legacy system still in production": traditional file-based PHP routing (no MVC framework), Apache with mod_php, MariaDB as the primary store, plus Redis (translation cache for i18n), a graph database, and a CDC sync pipeline on the side. The frontend serves search, statistical charts, and map visualizations — a single page can load several GeoJSON layer files.

The immediate driver was security: PHP 5.6 lost security support at the end of 2018, and MariaDB 10.4 is EOL too. But the system was also carrying real performance problems — the baseline load test showed that under 50 concurrent users in a mixed-browsing scenario, homepage p95 hit 23.99 seconds and the web container CPU saturated at 360%, while the database was practically asleep (under 2% CPU, zero slow-query growth).

That combination is a clear signal: **the bottleneck is the web tier, not the database.** It also means the usual optimization reflexes — add indexes, tune SQL — would accomplish nothing here. First you have to find out what the web tier is actually busy doing.

## My Role and Constraints

I owned this end to end: diagnosis, planning, implementation, deployment verification, and the client-facing report. One practical constraint ran through everything — **my development machine had no full production dataset** (a full database import takes hours). So the workflow had to be two-layered:

- **Whatever can be proven locally, prove with file-level evidence**: bytes before/after compression, page request counts, TCP connection counts — none of these need full data.
- **Whatever genuinely needs full data** (load tests, real query behavior) gets batched into one verification pass on the test server.

That constraint ended up shaping the entire methodology.

## Methodology: Three Deliberate Decisions

### Decision 1: One optimization, one commit, one measurement

I didn't batch the optimizations and measure once at the end. Every item shipped as its own commit with its own evidence:

| Item | Change | File-level evidence |
|---|---|---|
| A1 | GeoJSON MIME type + gzip | single file 4.14MB → 1.14MB (-72%) |
| A2 | Cache-Control on static assets (7 days) | no re-downloads on revisit |
| A3 | `loading="lazy"` on below-fold map iframe | 0 map requests before scroll |
| B1 | Homepage carousel: 251 images → 12, native lazy loading | carousel requests -95% |
| B2 | OPcache tuning | see "honest attribution" below |
| B3 | Batched i18n Redis lookups | 100+ connections/page → 1 |
| B4 | Offline compression of 30 large images | 21MB → 6MB |
| B5 | Deferred hidden iframes on results page | 412 requests/page → 6 |

Why insist on splitting? Because **if you change ten things and performance improves, you don't actually know which change did it.** The client will ask at acceptance. Whoever maintains this in six months will ask. And when something breaks and you need to roll back, you'll *really* ask. Attributability isn't report polish — it's a workflow design requirement.

### Decision 2: Honest attribution — the upgrade's gains don't belong to my optimizations

PHP 5.6 → 8.5 is itself a huge performance leap: a generation-newer engine. More importantly, I verified empirically that **the old container had no OPcache loaded at all** — every request re-parsed and re-compiled every PHP file — while the official PHP 8.5 image ships with OPcache built in and enabled by default.

That means the load-test delta is the *sum* of upgrade gains and optimization gains, and the two cannot be separated from aggregate numbers. So the report states them apart:

- **Transfer-volume metrics** (compression ratios, request counts, bytes per request) have file-level evidence and are attributed to specific optimizations.
- **CPU and latency metrics** are honestly reported as combined effects, with no single-item credit claimed.

One episode worth recording: I briefly believed the baseline load test had run on the new PHP, and on that basis overturned the "missing opcode cache causes high CPU" diagnosis as outdated thinking. Then a stakeholder corrected me — **the baseline was PHP 5.6** — and I immediately verified with `php -m` that the old container really had no OPcache: the original diagnosis had been reasonable, and I had over-corrected. That correction went into the work log verbatim.

In technical reporting, being willing to reverse your own conclusion matters as much as having good numbers. **"Optimizations alone achieved X; together with the upgrade, Y" is more convincing than one big vague number — and it survives follow-up questions.**

### Decision 3: One-sided changes beat synchronized two-sided changes

The frontend's i18n layer opened a fresh TCP connection to Redis for every translated string:

```php
// Original: every t() call → fsockopen → GET → fclose
function i18n_redis_get($key) {
    $fp = @fsockopen($host, $port, $errno, $errstr, 0.2);
    if (!$fp) return null;
    // ... send GET, read reply, close
}
```

One homepage render calls translation 100+ times — that's 100+ connection setups and teardowns. The textbook fix is storing each locale as a single JSON key, but that requires **changing both the writer (CMS) and the reader** and shipping them in lockstep; either side failing is an incident.

Reading the CMS sync code, I found that every time it writes a translation key it also maintains a SET index (`SADD i18n:keys ...`). So the reader could batch **unilaterally**:

```php
// After: one shared socket; SMEMBERS for all keys, MGET for the whole locale
$keys = i18n_redis_command(['SMEMBERS', 'i18n:keys']);
$values = i18n_redis_command(array_merge(['MGET'], $localeKeys));
// every subsequent t() hits a PHP array — zero network cost
```

100+ connections per page became 1, the CMS untouched, zero cross-system coordination. **Reading what the other system already gives you often downgrades a two-sided change into a one-sided one** — a completely different risk class.

## Four Debugging Stories

### The results page that made 412 requests

A user reported a search-results page "loading forever," with a DevTools screenshot: 412 requests, 102MB transferred, the same GeoJSON file downloaded ~20 times.

The cause: every table row embedded a map-preview modal, each containing an `<iframe src="map_preview?...">`. The key fact — **an iframe loads immediately even when hidden inside an unopened modal (`display:none`)**. Twenty result rows meant twenty full map pages, each pulling its own base maps, layer files, and tiles.

The fix defers loading until it's actually needed:

```html
<!-- src becomes data-src: no more auto-load -->
<iframe data-src="map_preview?sn=..." ...></iframe>
```

```js
// Load on first open of that row's modal; reopening reuses it
document.addEventListener('show.bs.modal', (e) => {
  const iframe = e.target.querySelector('iframe[data-src]');
  if (iframe && !iframe.hasAttribute('src')) {
    iframe.setAttribute('src', iframe.getAttribute('data-src'));
  }
});
```

Measured: page load went from 412 requests to **6**, and opening one preview loads exactly one map. One attribute plus ten lines of JS, -98% requests.

### The 40-second frozen homepage

During local testing the homepage would hang for 40+ seconds, looking like the whole service was down. Apache fine, PHP fine, database reachable — every component tested healthy in isolation.

The culprit was that same i18n layer — but this time its **failure mode**. The local environment happened to have no Redis running, and each translation key's `fsockopen` carried its own 0.2-second connect timeout. 100+ keys × 0.2s = 40+ seconds of accumulated waiting, after which each key falls back to its default string — so the page *eventually* renders, which is exactly what makes it look like a mysterious freeze.

Everyone talks about N+1 database queries, but **N+1 TCP connections become an N× timeout under failure** — merely slow when healthy, a disaster amplifier when not. The batching rewrite defused this too: a failed connection is cached per request, the 0.2s penalty is paid once, and everything falls back immediately.

### The map button that did nothing

Another user report: clicking the map icon on the results page did nothing at all. No error message, clean console, the button's HTML looked perfectly fine.

Silent failures like this cost the most time. Checking layer by layer in the browser, I found it: the page's markup used Bootstrap 5 syntax (`data-bs-toggle="modal"`), but **this one page was loading a Bootstrap 4 beta bundle from 2017** — which only understands `data-toggle`, doesn't recognize `data-bs-toggle`, and therefore does nothing and reports nothing. Every other page in the site had been migrated to Bootstrap 5.2; this page alone still referenced the old vendor file, presumably missed in some past upgrade.

The fix was one line: replace the old vendor trio (jquery + popper + BS4) with the site-wide `bootstrap.bundle.min.js` (after confirming the page had zero jQuery dependencies). **Frontend asset version mismatches don't throw errors — they just make features quietly disappear.** The cost of this class of bug isn't the fix; it's the finding.

### The metric trap: "total traffic went *up*"

Re-running the mixed load test after optimization: total bytes received went from 538MB to 607MB. At first glance that looks like a failed optimization — maybe even a regression.

Decomposed, the story flips: throughput was now 4.3× — the same 14 minutes completed 14,227 requests versus 3,330 before. The correct basis is **bytes per request: 165KB → 43KB (-74%)**. One layer deeper: the pre-optimization transfer rate sat pinned at 641kB/s — that was a bandwidth ceiling, meaning **throughput was being strangled by transfer volume**. With smaller requests, the same bandwidth budget does 4× the work.

The lesson: **define the metric wrong, and success looks like failure.** For any "total volume" acceptance target, always ask first: does this number still mean anything if throughput shifts dramatically?

## A Regression I Caused Myself — Twice

For the record, one mistake of my own, committed in two layers.

The homepage carousel rendered images via `<svg><image>`, which doesn't support native lazy loading, so for B1 I converted it to `<img loading="lazy">`. The layout promptly broke: slides of different heights. First layer: an `<img>` with `height:100%` needs a parent with a definite height, but the wrapping `<a>` was inline — the percentage had nothing to resolve against, so portrait images expanded to their intrinsic ratios. Fix: make the `<a>` `display:block;height:100%` so the height chain connects.

I thought that was the end of it — then the user sent two screenshots. The design intent was "portrait document image **fully visible and centered**, with a hand-drawn backdrop showing on both sides"; my `object-fit: cover` had cropped the image to fill and buried the backdrop entirely. Second layer: SVG `<image>`'s default scaling behavior (`xMidYMid meet`) is equivalent to CSS `contain`, not `cover`. One word, completely different visual.

This time I verified properly: actual browser rendering, cycling through slides of different aspect ratios, comparing against the original design before committing. The lesson in one line: **performance changes are UI changes — curl cannot verify visuals.** Every markup-touching change after that got verified with browser-rendered screenshots, not just HTML output.

## Load-Test Verification: All Four Tests Pass

The final verification ran on the test server (optimized build + full data) with the exact same k6 scripts as the baseline:

| Test | Scenario | Before | After |
|---|---|---|---|
| smoke (10 VUs) | homepage health check | — (new) | p95 83.99ms, pass |
| hot-search (50 VUs) | three search types | overall p95 9.55s | **52.58ms**, pass |
| mixed (50 VUs) | home + search + maps | home 23.99s / map 13.57s, **failing** | **76.92ms / 54.26ms**, pass |
| map-aggregation (20 VUs) | spatial aggregation | p95 3.1–3.6s, 5 EOFs | **37–44ms**, 7 EOFs (0.14%, within threshold) |

The monitoring told the same story: web container CPU fell from 243–363% to 6–22%; the DB connection high-water mark dropped from 101 to 7 — those 101 connections had been a **symptom** of PHP workers queueing up (each queued request holding a DB connection), and they evaporated once the web tier got fast. A `SHOW PROCESSLIST` captured mid-test even showed the carousel query's `LIMIT 12` — handy deployment evidence that the system under test really was the optimized build.

Residuals are recorded honestly too: a small number of EOFs (0.14%) remain, but with web CPU now ruled out as a saturation cause, the investigation narrows to reverse-proxy/container timeout alignment — next round's work, and not material to the 50-user verdict.

## Migration Landmine Checklist (PHP 5.6 → 8.x, MariaDB 10.x → 11.x)

The traps I hit and cleared, for anyone walking the same road:

- **MariaDB 11.x removed the `mysql`/`mysqldump`/`mysqladmin` command names** — only `mariadb-*` remains. Ops scripts, backup/restore, docker healthchecks: all of it. The good news: the 10.4 image carries *both* names, so you can **switch everything early**, run compatibly on both versions, and carry zero script risk on upgrade day.
- **Datadirs can't be upgraded in place across major versions.** Always: fresh data directory + dump re-import, keeping the old directory until verification completes (that's your rollback).
- **PHP 8 promoted undefined variables from Notice to Warning.** Legacy code that echoes never-assigned variables in no-data branches was invisible on 5.6 and prints warnings onto the page in 8.x. Keep `display_errors` on in development deliberately — it's a free compatibility scanner — and off in production (warnings belong in logs), which is also the security-correct choice.
- **mysqli throws exceptions by default since PHP 8.1** (`MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT`). Legacy code is full of "query returns false, check it yourself" patterns; after upgrade the same situation becomes an uncaught exception and a full-page 500. Restoring the old behavior globally with `mysqli_report(MYSQLI_REPORT_OFF)` is far more pragmatic than adding try-catch to every file.
- **Official PHP images changed their OPcache behavior across versions**: 8.5 bundles and enables it by default, and `docker-php-ext-install opcache` actually *breaks* the build. Run `php -v` before attributing performance gains — don't book the platform's win as your config change.
- **Windows dev-environment silent killers** (if your team is cross-platform): Git Bash's MSYS path conversion rewrites docker args like `-w /work` into `C:/Program Files/Git/work`; the built-in `convert.exe` (an NTFS utility) shadows ImageMagick's `convert`. Guard both in scripts.

## Closing

The biggest takeaway isn't the numbers — it's the validated practice: **treat attributability as a first-class requirement of the workflow.** Every change committed separately, measured separately, with honest bookkeeping of which gains were mine and which belonged to the platform — including filing my own misjudgment and the regression I caused.

Numbers talk. But only numbers that survive interrogation are worth talking about.
