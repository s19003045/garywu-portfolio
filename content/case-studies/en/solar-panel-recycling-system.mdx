## Project Background

A solar panel recycling system with the goal of fully digitalising the recycling process — from on-site device panel identification and automated processing, to cloud-based order management and production tracking — forming a complete edge-to-cloud data loop.

The project spanned 15+ repositories and involved integration across multiple organisations and technical layers, making it one of the largest and most technically complex projects I've participated in.

## Core Challenges

### Real-World Industrial Constraints

- **Unstable networking**: Factory floor networks cannot guarantee stable connectivity
- **Resource-constrained IPC**: Edge devices have limited compute resources — they can't scale like cloud servers
- **Multi-version concurrency**: Devices evolved from 1.0 to 2.x, requiring version difference support without major rewrites
- **Cross-company collaboration**: Long-term technical collaboration with the equipment manufacturer's engineering team, requiring precise requirement alignment

### Complexity of System Integration

The following systems needed to operate in coordination:
- 5 IPC edge modules
- PLC communication (OPC UA)
- SCADA monitoring system
- AI object recognition model (YOLOv11)
- 3 Cloud APIs
- IPFS verifiable file storage
- Order management system
- Plant management system

## My Role and Contributions

### IPC Core Program Architecture Design

Responsible for designing and developing the IPC core program — the edge-side heart of the entire system. The core program needed to:

- Bridge PLC communication, reading device status and control commands in real time
- Coordinate the workflows of 5 IPC edge modules
- Integrate AI inference results into the recycling decision flow
- Manage image capture and local storage
- Handle recycling data uploads to the cloud

### Config-Driven Multi-Version Architecture

For the version management challenge, I designed a config-driven architectural approach:

```
Device 1.0 ──────────────────────────────────────────────────
Device 2.x ──────────────────────────────────────────────────
                              ↓
                   Single IPC Core Program
                              ↓
         Version differences isolated to config files
```

This concentrated version differences in configuration management rather than program logic, **reducing redundant development work by approximately 75%**.

### Deployment Efficiency: An IPC Software Version Manager

Installing the core program, multiple edge modules, and AI models by hand — device by device, item by item — was slow and error-prone across versions and dependencies. I introduced an IPC software version manager that turned deployment into a controlled, repeatable process: per-device deployment dropped from roughly **1 hour to 15 minutes**, while sharply cutting the risk of manual installation errors across the core program, modules, and AI models. On a floor running multiple versions across multiple sites, every update became both faster and more reliable.

### End-to-End Traceability: 21 Process Timestamps per Panel

The recycling flow spans **7 key stations**, and the system records **21 process timestamps** for every panel — plus a process record at each station — capturing each panel's full journey from intake to completed recycling. All recycling data and system logs sync to the cloud and are **retained for at least 5 years**, so any panel and any process step can be precisely traced and analysed after the fact.

This traceability rests on monitoring at multiple levels of granularity:

- **Plant level**: SCADA monitors overall line status in real time
- **Device level**: tracks each device's recycling throughput and operating status
- **Station level**: process records for each of the 7 key stations
- **Panel level**: full traceability via 21 timestamps per panel

From coarse to fine, both the floor and the cloud can grasp production state at the right granularity.

### Observability: Log System Overhaul, 3x Faster Troubleshooting

Early on, device logs mostly stayed on the local IPC. To debug, an engineer had to remote into the device and dig through logs — but with no proper interface or categorisation, the logs existed yet were extremely noisy, and pinpointing a problem routinely took tens of minutes, sometimes far longer.

I overhauled the entire logging mechanism:

- **Levels**: classified logs into 6 severity levels, from routine info to fatal errors
- **Categories & events**: tagged by category and event so logs became structured and queryable
- **Scheduled cloud upload**: logs pushed up regularly so engineers could monitor in real time on SCADA — no more remote-logging into devices to search
- **Filter-based localisation**: filter by level, category, event, and time to quickly narrow scope, then analyse root cause

The structured logging spans **764 log call sites across 6 levels, 61 module categories, and 52 event categories** — covering API requests and responses, scheduled tasks, OPC communication, device reads/writes, connection status, storage flows, data upload and resend, permission checks, and alert notifications. Almost every critical path leaves a traceable trail, sharply improving on-site problem localisation.

Result: localisation time varies with problem complexity, but overall lookup-and-localisation **efficiency improved by ~3x (roughly two-thirds less time)**. For example, a lookup that once took ~60 minutes could drop to under 20. This is what makes an "integrated system" genuinely maintainable: you can only stop the bleeding fast if you can observe it.

### Edge-to-Cloud Data Sync: 100% Eventual Success, 99.9% Availability

Every device produces a large volume of recycling records and timestamps each day, and all of it has to reach the cloud reliably. My Edge-to-Cloud sync mechanism runs on two tracks — **real-time upload plus scheduled retry on failure**: it syncs immediately under normal conditions, and when the site loses connectivity or the cloud is momentarily unavailable, data enters a scheduled queue and keeps retrying until it lands. This achieves a **100% eventual data-sync success rate** even on unstable factory networks, meeting a **99.9% system availability** requirement.

### Data Resilience: Off-site Cloud Backup of the IPC Database

For unstable field networks and constrained edge resources, I designed a scheduled backup mechanism: periodically backing up the IPC database to the cloud for **off-site disaster recovery (DR)**, keeping the recovery point objective (RPO) within **24 hours** so critical data stays recoverable even if a device or site fails.

## Lessons Learned

The biggest takeaway from this project was a deep understanding of the complexity of industrial system integration — the problems often aren't just technical implementation. More often they involve:

1. **Understanding real constraints**: Field network, device resources, and operator habits all differ from development environments
2. **Designing evolvable architecture**: Systems need to remain maintainable through continuously changing requirements
3. **Cross-organisational technical communication**: Gaps in requirement understanding are often harder to solve than technical problems
