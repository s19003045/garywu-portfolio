## 專案背景

客戶要在展場以 iPad 展示一個 React.js 開發的網站，內容包含多支影片。問題是：**展場提供的網路頻寬極低**，導致影片載入與播放嚴重延遲，現場體驗大打折扣。

影片已經做過壓縮，但仍無法改善——因為瓶頸不在檔案大小，而在**網路環境本身**。

## 核心挑戰

這個案例的限制條件很特殊，幾個常見解法都被排除：

- **不能刪影片**：影片是展示的重點內容，無可取代
- **不能只靠壓縮**：已壓縮過，再壓畫質就不堪用
- **網站還要頻繁改**：展前內容持續調整，不能整包打死成離線檔
- **跑在 iPad 上**：沒有完整作業系統，部署環境受限

換句話說，問題的本質不是「網站寫得對不對」，而是「**系統如何適配一個網路極差的實際環境**」——這正是我反覆遇到的那類問題。

## 解決方案

### 核心思路：把影片來源搬到設備本地

既然遠端網路是瓶頸，那就讓**影片不要走網路**。我的方案是直接在 iPad 上架一個本地 API 伺服器，讓網站的影片請求打到 `localhost`，圖片等其他資源則維持走遠端——這樣既消除影片卡頓，又保留網站的遠端更新彈性。

### 技術實作

在 iPad（iPadOS）上要跑伺服器並不直覺，我用了這套組合：

- **iSH**：iOS/iPadOS 上基於 Alpine Linux 的 Linux Shell 環境，讓 iPad 能跑 Linux 工具
- **Alpine Linux + apk**：以 `apk` 套件管理器安裝所需工具
- **Python API 伺服器**：負責供應本地影片檔
- **OpenRC**：Alpine 的服務管理，設定伺服器隨 iSH 啟動自動運行
- **Shell Script**：自動化整個啟動流程，降低現場操作複雜度

實作步驟大致如下：

1. 透過 Google Drive 將 Python 專案與影片下載到 iPad
2. 用 iSH 的 mount 功能連接 iPad 檔案系統，取得影片檔
3. 以 OpenRC 設定本地 API 伺服器為自啟動服務，並保持背景執行
4. 調整展示版網站：**影片請求指向本地 API，圖片請求維持遠端**

## 成果

- **影片播放完全不再受展場網速影響**——因為根本不再經過網路
- **保留遠端資源彈性**：圖片等非關鍵資源仍可遠端更新，展前修改不受影響
- **現場操作簡化**：自啟動 + 背景執行，展場人員不需手動下指令

## 反思

這個案例和我處理過的多數效能問題有一個共同點：**真正的瓶頸往往不在程式邏輯，而在系統與實際環境的適配。**

與其在「正確的程式」上反覆打轉，不如退一步問：這個系統實際要在什麼環境下運作？當你把「低網速」當成設計前提，而不是意外狀況，解法的方向就完全不同了——有時候答案不是優化請求，而是**讓關鍵資源根本不要上路**。
