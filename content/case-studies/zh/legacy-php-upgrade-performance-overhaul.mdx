一套服役多年的歷史檔案檢索系統(PHP 5.6 + MariaDB 10.4),因資安要求必須升級到 PHP 8.5 + MariaDB 11.8。我藉這次升級,同時處理了長年累積的效能問題。

先看結果——腳本與門檻一字不改的前後壓測:

| 指標 | 優化前 | 優化後 | 改善 |
|---|---|---|---|
| 首頁 p95(50 VUs 混合壓測) | 23.99 秒(未達標) | **76.92 毫秒** | -99.7% |
| 地圖頁 p95 | 13.57 秒(未達標) | **54.26 毫秒** | -99.6% |
| Web 容器 CPU 峰值 | ~360%(滿載) | **~22%** | 形同輕載 |
| 資料庫連線高水位 | 101 | **7** | 連線堆積消失 |
| 吞吐量 | 3.96 req/s | 16.91 req/s | +327% |

50 人併發的四支 k6 測試全數通過,零 HTTP 錯誤。

## 我的角色與限制

這個案子由我獨立負責:從診斷、規劃、實作到部署驗證。有一個現實限制貫穿全程——**開發機沒有完整的正式資料**(全量資料庫匯出入以小時計),所以整個優化流程必須設計成:能在本機用檔案層級證據驗證的先驗證,必須靠測試機的(壓測、全量資料行為)留到最後一次驗完。

這個限制反而塑造了整個案子的方法論。

## 方法論:三個刻意的決策

### 1. 每項優化一個 commit、一次量測

我沒有把所有優化一口氣改完再測。每個項目獨立 commit,附上自己的量測證據:GeoJSON 壓縮前後的 bytes、頁面請求數的變化、Redis 連線數。原因很簡單:**改了十個地方之後效能變好,你其實不知道是哪個改動的功勞**——而客戶驗收與後續維運,需要知道。

### 2. 誠實歸因:升級的功勞不能算在優化頭上

PHP 5.6 → 8.5 本身就會帶來大幅效能提升:引擎快了一個世代,而且實測發現舊容器**根本沒有啟用 OPcache**,新版官方 image 則預設內建啟用。這意味著壓測數字的改善,是「版本升級」與「優化項目」兩種效益的合計。

我在報告裡把這兩者明確分開:傳輸量類指標(壓縮、減量)有檔案層級證據,可以歸因給具體優化;CPU 與延遲類指標則誠實寫成合計效果。**「單靠優化達到 X,加上升級合計達到 Y」比一個籠統的大數字更有說服力,也經得起追問。**

過程中我還修正了自己的一次誤判:我一度以為基線壓測是在新版 PHP 上跑的,據此推翻了「缺編譯快取導致高 CPU」的診斷——後來確認基線其實是 PHP 5.6(無 OPcache),原診斷是合理的,是我過度更正。這條修正也如實寫進了工作日誌。

### 3. 單邊改動優於雙邊同步改

前台的多語系機制,每個翻譯字串都會各開一條 TCP 連線去查 Redis——首頁一次渲染要開 100 多條。教科書解法是把整包翻譯改存成單一 JSON key,但那需要**同時改寫入端(CMS)和讀取端**,兩個系統要同步上線。

我翻了 CMS 的同步程式,發現它本來就維護著一個所有 key 的 SET 索引——所以讀取端可以單方面用 `SMEMBERS` + `MGET` 一次載入整個語系,寫入端一行都不用動。每頁 100+ 條連線變 1 條,而且零跨系統協調成本。

## 三個破案現場

### 一頁 412 個請求的檢索結果頁

使用者回報某個檢索結果頁「載入很久」,DevTools 顯示 412 個請求、102MB 傳輸量,同一個 GeoJSON 檔被重複下載約 20 次。

追查發現:結果表每一列都內嵌一個地圖預覽 modal,每個 modal 裡有一個 `<iframe>`。**iframe 就算藏在還沒打開的 modal 裡(`display:none`),瀏覽器照樣立刻載入**——20 列就是 20 份完整的地圖頁,每份各自去拉底圖和圖層檔。

修法是把 `src` 改成 `data-src`,監聽 Bootstrap 的 `show.bs.modal` 事件,第一次打開才真正載入。412 個請求變 6 個。

### 40 秒的假死首頁

本機測試時首頁莫名卡 40 秒以上,看起來像整個服務掛掉。追進去發現是上面提到的 i18n 機制:Redis 連不到時,**每個翻譯 key 各自付 0.2 秒的連線 timeout**,100 多個 key 疊起來就是 40 秒。N+1 問題大家都講資料庫,但 N+1 的 TCP 連線在故障時會變成 N 倍的 timeout——**故障放大器**。批次化改造順手把這顆雷也拆了:連線失敗只付一次,之後直接走 fallback 文字。

### 「總流量沒降反升」的指標陷阱

優化後的混合壓測,總接收量從 538MB 變成 607MB——看起來像失敗?其實吞吐量變成 4.3 倍,同樣 14 分鐘完成了 4.3 倍的請求。正確的比較是**每請求接收量:165KB → 43KB(-74%)**。優化前 641kB/s 的固定速率其實是頻寬上限,吞吐被傳輸量卡死;優化後同樣的頻寬預算能做 4 倍多的事。

**指標定義錯了,成功會看起來像失敗。**設定驗收目標時,任何「總量」指標都要先問:如果吞吐量大幅變動,這個指標還有意義嗎?

## 一次自己造成的視覺回歸

也記錄一個我自己犯的錯。首頁輪播原本用 `<svg><image>` 呈現(不支援原生 lazy loading),我改成 `<img loading="lazy">` 時用了 `object-fit: cover`——上線一看,設計原意是「直式檔案圖完整置中、兩側露出手繪底圖」,`cover` 把底圖整個蓋掉了。原本 SVG 的預設行為等同 `contain`,兩個字的差別,視覺完全不同。

靠使用者的截圖回報和瀏覽器實際渲染比對才修對。教訓一句話:**效能改動也是 UI 改動,curl 驗不出視覺**。此後所有涉及 markup 的變更,我都改用瀏覽器渲染截圖驗證,不再只看 HTML 輸出。

## 升級遷移地雷清單(PHP 5.6 → 8.x、MariaDB 10.x → 11.x)

最後整理這次踩過、修掉的地雷,給要走同一條路的人:

- **MariaDB 11.x 移除了 `mysql`/`mysqldump`/`mysqladmin` 指令名**,只剩 `mariadb-*` 系列。所有腳本與 healthcheck 都要換——而且 10.4 的 image 兩種名稱都有,可以提前改成新名稱,升級當天零腳本風險。
- **跨大版本的 datadir 不能原地升級**,一律全新資料夾 + dump 重匯,舊資料夾保留到驗證完成(rollback 用)。
- **PHP 8 把 undefined variable 從 Notice 升級成 Warning**:老程式碼「沒資料的分支直接 echo 未賦值變數」的寫法,在 5.6 是隱形的,在 8.x 會把警告直接印在頁面上。`display_errors` 在正式環境務必關閉(warning 進 log 就好),這同時也是資安要求——別把路徑和程式結構印給使用者。
- **前端資產的版本錯配會靜默失效**:某頁的 modal 點了沒反應,查下去是頁面 markup 已是 Bootstrap 5(`data-bs-toggle`)、但該頁引用的 JS 還是 2017 年的 Bootstrap 4 beta——它只認 `data-toggle`,所以什麼都不做、也不報錯。全站只有那一頁還在用舊檔。
- **官方 PHP image 的 OPcache 行為隨版本變了**:8.5 已內建並預設啟用,`docker-php-ext-install opcache` 反而會 build 失敗。做效能歸因前,先 `php -v` 確認現況,別把版本自帶的效益記到自己的設定頭上。

## 結語

這個案子最大的收穫不是那些漂亮的數字,而是驗證了一套做法:**把「可歸因」當成一級需求來設計工作流程**——每個改動獨立提交、獨立量測、誠實區分哪些功勞是自己的、哪些是平台的。數字會說話,但只有經得起追問的數字才值得說。
