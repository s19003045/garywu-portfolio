一套服役多年的歷史檔案檢索系統(PHP 5.6 + MariaDB 10.4),因資安要求必須升級到 PHP 8.5 + MariaDB 11.8。我藉這次升級,同時處理了長年累積的效能問題。

先看結果——壓測腳本與驗收門檻一字不改的前後對照:

| 指標 | 優化前 | 優化後 | 改善 |
|---|---|---|---|
| 首頁 p95(50 VUs 混合壓測) | 23.99 秒(未達標) | **76.92 毫秒** | -99.7% |
| 地圖頁 p95 | 13.57 秒(未達標) | **54.26 毫秒** | -99.6% |
| 搜尋整體 p95 | 9.55 秒 | **52.58 毫秒** | -99.4% |
| Web 容器 CPU 峰值 | ~360%(滿載) | **~22%** | 形同輕載 |
| 資料庫連線高水位 | 101 | **7** | 連線堆積消失 |
| 混合情境吞吐量 | 3.96 req/s | **16.91 req/s** | +327% |
| 首頁瀏覽器請求數 | ~297 | **17** | -94% |
| 首頁完成載入 | 7.22 秒 | **264 毫秒** | -96% |

50 人併發的四支 k6 測試全數通過,零 HTTP 錯誤。這篇文章記錄整個過程:怎麼診斷、怎麼決定改什麼、踩了哪些雷、以及一個我自己造成又修回來的視覺回歸。

## 專案背景

這套系統是典型的「還在營運的遺留系統」:傳統 PHP 檔案路由(非 MVC 框架)、Apache + mod_php、MariaDB 為主資料庫,旁邊還掛著 Redis(多語系翻譯快取)、圖資料庫與 CDC 同步管線。前台提供檢索、統計圖表與地圖視覺化,單頁會載入多個 GeoJSON 圖層檔。

升級的直接動機是資安:PHP 5.6 在 2018 年底就終止安全支援,MariaDB 10.4 也已 EOL。但系統同時背著效能問題——優化前的壓力測試顯示,50 名同時使用者的混合瀏覽情境下,首頁 p95 高達 23.99 秒,Web 容器 CPU 衝到 360% 徹底滿載,而資料庫幾乎在睡覺(CPU 不到 2%、慢查詢零增長)。

這個組合給了一個明確的訊號:**瓶頸在 Web 層,不在資料庫**。也意味著加索引、調 SQL 這類「常見優化直覺」在這裡不會有用——得先弄清楚 Web 層到底在忙什麼。

## 我的角色與限制

這個案子由我獨立負責:診斷、規劃、實作、部署驗證、產出客戶報告。有一個現實限制貫穿全程——**開發機沒有完整的正式資料**(全量資料庫匯出入以小時計),所以整個工作流程必須設計成兩層:

- **本機能驗證的,用檔案層級證據驗證**:壓縮前後的位元組數、頁面請求數、TCP 連線數——這些不需要全量資料。
- **必須靠全量資料的(壓測、真實查詢行為),集中到測試機一次驗證**。

這個限制反而塑造了整個案子的方法論。

## 方法論:三個刻意的決策

### 決策一:每項優化一個 commit、一次量測

我沒有把所有優化一口氣改完再測。每個項目獨立 commit,附上自己的量測證據。改動清單長這樣:

| 項目 | 內容 | 檔案層級證據 |
|---|---|---|
| A1 | GeoJSON 設定 MIME type + gzip 壓縮 | 單檔 4.14MB → 1.14MB(-72%) |
| A2 | 靜態資源加 Cache-Control(7 天) | 回訪不再重新下載 |
| A3 | 首屏下方的地圖 iframe 加 `loading="lazy"` | 未捲動前 0 個地圖請求 |
| B1 | 首頁輪播 251 張圖減至 12 張 + 原生 lazy loading | 輪播請求 -95% |
| B2 | OPcache 參數調校 | 見「誠實歸因」一節 |
| B3 | 多語系 Redis 查詢批次化 | 每頁連線 100+ → 1 |
| B4 | 30 張大圖離線壓縮 | 21MB → 6MB |
| B5 | 檢索結果頁的隱藏 iframe 延遲載入 | 單頁請求 412 → 6 |

為什麼堅持拆開?因為**改了十個地方之後效能變好,你其實不知道是哪個改動的功勞**。客戶驗收會問、半年後接手維運的人會問、出問題要回滾的時候更會問。「可歸因」不是報告的修飾,是工作流程的設計需求。

### 決策二:誠實歸因——升級的功勞不能算在優化頭上

PHP 5.6 → 8.5 本身就是巨大的效能躍遷:引擎快了一個世代。更關鍵的是,我實測發現**舊容器根本沒有載入 OPcache**——每個請求都在重新解析、編譯所有 PHP 檔;而 PHP 8.5 的官方 image 預設就內建並啟用 OPcache。

這意味著壓測數字的改善,是「版本升級」與「優化項目」兩種效益的**合計**,而且兩者從壓測總量裡拆不開。我在報告裡明確分開陳述:

- **傳輸量類指標**(壓縮率、請求數、每請求接收量)有檔案層級證據,可以歸因給具體優化項目。
- **CPU 與延遲類指標**誠實寫成合計效果,不宣稱是哪個單項的功勞。

這裡還有一段值得記錄的過程:我一度以為基線壓測是在新版 PHP 上跑的,據此推翻了「缺編譯快取導致高 CPU」的診斷,認為那是過時的判斷。後來與利害關係人確認——**基線其實是 PHP 5.6**,我立刻用 `php -m` 實測驗證了舊容器確實沒有 OPcache:原診斷是合理的,是我過度更正。這條修正如實寫進了工作日誌。

做技術報告,「敢改自己的結論」跟「數字漂亮」一樣重要。**「單靠優化達到 X,加上升級合計達到 Y」比一個籠統的大數字更有說服力,也經得起追問。**

### 決策三:單邊改動優於雙邊同步改

前台的多語系機制,每個翻譯字串都會各開一條 TCP 連線去查 Redis:

```php
// 原始寫法:每個 t() 呼叫 → fsockopen → GET → fclose
function i18n_redis_get($key) {
    $fp = @fsockopen($host, $port, $errno, $errstr, 0.2);
    if (!$fp) return null;
    // ... 送 GET 指令、讀回應、關閉連線
}
```

首頁一次渲染呼叫 100 多次翻譯,就是 100 多條連線的建立與拆除。教科書解法是把整包翻譯改存成單一 JSON key——但那需要**同時改寫入端(CMS)和讀取端**,兩個系統要同步上線,任何一邊出錯都是事故。

我翻了 CMS 的同步程式,發現它寫入每個翻譯 key 時,本來就同步維護著一個 SET 索引(`SADD i18n:keys ...`)。所以讀取端可以**單方面**批次化:

```php
// 改造後:一條共用 socket,SMEMBERS 拿全部 key,MGET 一次取回整個語系
$keys = i18n_redis_command(['SMEMBERS', 'i18n:keys']);
$values = i18n_redis_command(array_merge(['MGET'], $localeKeys));
// 之後所有 t() 呼叫都打 PHP 陣列,零網路成本
```

每頁 100+ 條連線變 1 條,CMS 一行都不用動,零跨系統協調成本。**先讀懂對方系統已經給你的東西,常常能把雙邊改動降級成單邊改動**——風險等級完全不同。

## 四個破案現場

### 一頁 412 個請求的檢索結果頁

使用者回報某個檢索結果頁「載入很久」,附上 DevTools 截圖:412 個請求、102MB 傳輸量,同一個 GeoJSON 檔被重複下載約 20 次。

追查發現:結果表每一列都內嵌一個地圖預覽 modal,每個 modal 裡有一個 `<iframe src="map_preview?...">`。關鍵在於——**iframe 就算藏在還沒打開的 modal 裡(`display:none`),瀏覽器照樣立刻載入**。20 列結果就是 20 份完整的地圖頁面,每份各自去拉底圖、圖層檔、圖磚。

修法是延遲到真正需要時才載入:

```html
<!-- src 改成 data-src,不再自動載入 -->
<iframe data-src="map_preview?sn=..." ...></iframe>
```

```js
// 第一次打開該列的 modal 才填入 src;重開直接重用
document.addEventListener('show.bs.modal', (e) => {
  const iframe = e.target.querySelector('iframe[data-src]');
  if (iframe && !iframe.hasAttribute('src')) {
    iframe.setAttribute('src', iframe.getAttribute('data-src'));
  }
});
```

實測:頁面載入從 412 個請求變 **6 個**,打開一個預覽視窗恰好載入一份地圖。一個屬性加十行 JS,-98% 的請求量。

### 40 秒的假死首頁

本機測試時首頁莫名卡 40 秒以上,看起來像整個服務掛掉。Apache 正常、PHP 正常、資料庫連得上——單獨測每個組件都沒問題。

真兇還是上面那個 i18n 機制,但這次是它的**故障模式**:本機環境剛好沒起 Redis,而每個翻譯 key 的 `fsockopen` 各自帶 0.2 秒的連線 timeout。100 多個 key × 0.2 秒 = 40 秒以上的累積等待,然後每個 key 各自 fallback 到預設文字——所以頁面「最終會出來」,看起來就像假死。

N+1 問題大家都講資料庫查詢,但 **N+1 的 TCP 連線在故障時會變成 N 倍的 timeout**——正常時只是慢,故障時是災難放大器。批次化改造順手把這顆雷拆了:共用 socket 的連線失敗會被快取,整個請求只付一次 0.2 秒,之後直接走 fallback。

### 點了沒反應的地圖按鈕

另一個使用者回報:結果頁的地圖圖示點了沒有任何反應。沒有錯誤訊息、console 乾淨、按鈕的 HTML 看起來完全正常。

這種「靜默失效」最花時間。我在瀏覽器裡逐層檢查,最後發現:頁面的 markup 用的是 Bootstrap 5 語法(`data-bs-toggle="modal"`),但**這一頁引用的 JS 是 2017 年的 Bootstrap 4 beta**——它只認 `data-toggle`,看不懂 `data-bs-toggle`,所以什麼都不做、也不報錯。全站其他頁面都已經升到 Bootstrap 5.2,只有這一頁還在載入舊的 vendor 檔,大概是某次升版時漏改的。

修法一行:把舊 vendor 三件套(jquery + popper + BS4)換成全站共用的 `bootstrap.bundle.min.js`(確認過該頁沒有任何 jQuery 依賴)。**前端資產的版本錯配不會報錯,它只會讓功能安靜地消失**——這種 bug 的成本不在修,在找。

### 「總流量沒降反升」的指標陷阱

優化後重跑混合壓測,總接收量 538MB → 607MB。乍看像優化失敗,甚至像回歸。

拆開看才知道:吞吐量變成了 4.3 倍——同樣 14 分鐘,優化前完成 3,330 個請求,優化後完成 14,227 個。正確的比較基準是**每請求接收量:165KB → 43KB(-74%)**。再深一層:優化前的傳輸速率穩定卡在 641kB/s,那其實是頻寬上限——**吞吐量是被傳輸量掐死的**。優化後每個請求變小,同樣的頻寬預算就能完成 4 倍以上的工作。

這件事教的是:**指標定義錯了,成功會看起來像失敗**。任何「總量」型的驗收指標,都要先問一句:如果吞吐量大幅變動,這個數字還有意義嗎?

## 一次自己造成的視覺回歸

也記錄一個我自己犯的錯,而且犯了兩層。

首頁輪播原本用 `<svg><image>` 呈現圖片。SVG 的 `<image>` 不支援原生 lazy loading,所以 B1 優化時我把它換成 `<img loading="lazy">`。上線一看,輪播跑版了:有的 slide 高、有的矮。第一層錯:`<img>` 的 `height:100%` 需要父層有明確高度才能解析,但外層的 `<a>` 是 inline 元素——百分比高度沒有著力點,直式圖片就按原始比例撐開了。修法:`<a>` 改 `display:block;height:100%`,讓高度鏈接通。

改完自認沒問題,結果使用者傳來兩張截圖:設計的原意是「直式檔案圖**完整置中**,兩側露出手繪風格的底圖」;我用的 `object-fit: cover` 把圖放大裁切、底圖整個蓋掉了。第二層錯:原本 SVG `<image>` 的預設縮放行為(`xMidYMid meet`)等同 CSS 的 `contain`,不是 `cover`。兩個單字的差別,視覺完全不同。

這次我學乖了:改用瀏覽器實際渲染、切換多張不同長寬比的 slide 逐一比對,確認與原始視覺一致才提交。教訓一句話:**效能改動也是 UI 改動,curl 驗不出視覺**。此後所有涉及 markup 的變更,一律以瀏覽器渲染截圖驗證,不再只看 HTML 輸出。

## 壓測驗證:四支測試全數通過

最終在測試機(部署優化後版本 + 全量資料)重跑與基線完全相同的 k6 腳本:

| 測試 | 情境 | 優化前 | 優化後 |
|---|---|---|---|
| smoke(10 VUs) | 首頁健檢 | -(新增) | p95 83.99ms,通過 |
| hot-search(50 VUs) | 三種檢索 | 整體 p95 9.55s | **52.58ms**,通過 |
| mixed(50 VUs) | 首頁+檢索+地圖 | home 23.99s / 地圖頁 13.57s,**未達標** | **76.92ms / 54.26ms**,通過 |
| map-aggregation(20 VUs) | 空間聚合查詢 | p95 3.1~3.6s,5 筆 EOF | **37~44ms**,7 筆 EOF(0.14%,門檻內) |

監測面同樣有感:Web 容器 CPU 從 243~363% 降到 6~22%;資料庫連線高水位從 101 掉到 7——優化前那 101 條連線其實是 PHP worker 排隊堆積的**症狀**(每個排隊請求各占一條 DB 連線),Web 層變快之後自然消失。測試期間順手抓的 `SHOW PROCESSLIST` 還拍到輪播查詢的 `LIMIT 12`,正好當作「受測的確實是優化後版本」的部署證據。

殘餘項也如實記錄:少量 EOF(0.14%)仍在,但 Web CPU 已排除飽和因素,追查方向收斂到反向代理與容器之間的 timeout 對齊——這是下一輪的事,不影響 50 人目標的判定。

## 升級遷移地雷清單(PHP 5.6 → 8.x、MariaDB 10.x → 11.x)

最後整理這次踩過、修掉的雷,給要走同一條路的人:

- **MariaDB 11.x 移除了 `mysql`/`mysqldump`/`mysqladmin` 指令名**,只剩 `mariadb-*` 系列。維運腳本、備份還原、docker healthcheck 全部要換。好消息是 10.4 的 image 兩種名稱都有——**可以提前全部改成新名稱**,兩版通吃,升級當天零腳本風險。
- **跨大版本的 datadir 不能原地升級**。一律全新資料目錄 + dump 重匯,舊目錄保留到驗證完成(那是你的 rollback)。
- **PHP 8 把 undefined variable 從 Notice 升級成 Warning**。老程式碼「查無資料的分支直接 echo 未賦值變數」的寫法,在 5.6 是隱形的,在 8.x 會把警告直接印在頁面上。開發環境刻意開著 `display_errors` 當作相容性掃描器,正式環境務必關閉(警告進 log 就好)——這同時是資安要求:別把路徑和程式結構印給使用者。
- **PHP 8.1+ 的 mysqli 預設丟例外**(`MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT`)。老程式碼滿地都是「查詢失敗回傳 false 再自行判斷」的寫法,升級後同一個情境會變成未捕捉例外、整頁 500。用 `mysqli_report(MYSQLI_REPORT_OFF)` 全域還原舊行為,比逐檔加 try-catch 務實得多。
- **官方 PHP image 的 OPcache 行為隨版本變了**:8.5 已內建並預設啟用,`docker-php-ext-install opcache` 反而會 build 失敗。做效能歸因前先 `php -v`,別把平台自帶的效益記到自己的設定頭上。
- **Windows 開發環境的隱形殺手**(如果你的團隊跨平台):Git Bash 的 MSYS 路徑轉換會把 docker 參數 `-w /work` 改寫成 `C:/Program Files/Git/work`;系統內建的 `convert.exe`(NTFS 工具)會跟 ImageMagick 撞名。腳本裡都要防。

## 結語

這個案子最大的收穫不是那些漂亮的數字,而是驗證了一套做法:**把「可歸因」當成一級需求來設計工作流程**——每個改動獨立提交、獨立量測、誠實區分哪些功勞是自己的、哪些是平台的,連自己的誤判和造成的回歸也如實入檔。

數字會說話,但只有經得起追問的數字才值得說。
