## 專案背景

這是一個太陽能板回收系統，目標是將整個回收流程數位化——從現場設備端的板片辨識、自動化處理，到雲端的訂單管理與生產追蹤，形成完整的 edge-to-cloud 資料閉環。

專案橫跨 15+ repositories，涉及多個組織與技術層面的整合，是我參與過規模最大、技術複雜度最高的專案之一。

## 核心挑戰

### 工業現場的真實限制

- **網路不穩定**：工廠現場的網路環境無法保證穩定連線
- **IPC 資源受限**：邊緣端設備計算資源有限，不能像雲端伺服器一樣無限擴展
- **多版本並行**：設備從 1.0 演進至 2.x，需要在不大幅改寫的前提下支援版本差異
- **跨公司協作**：與設備商工程部的長期技術協作，需要精準的需求溝通與對齊

### 系統整合的複雜度

需要讓以下系統協同運作：
- 5 個 IPC edge modules
- PLC 通訊（OPC UA）
- SCADA 監控系統
- AI 物件辨識模型（YOLOv11）
- 3 個 Cloud APIs
- IPFS 可驗證檔案儲存
- 訂單管理系統
- 廠務系統

## 我的角色與貢獻

### IPC 主程式架構設計

負責設計並開發 IPC 主程式，這是整個系統的邊緣端核心。主程式需要：

- 串聯 PLC 通訊，即時讀取設備狀態與控制指令
- 協調 5 個 IPC edge modules 的工作流程
- 整合 AI 推論結果到回收決策流程
- 管理影像擷取與本地存儲
- 處理回收數據上傳至雲端

### Config-Driven 多版本架構

針對版本管理挑戰，設計了 config-driven 的架構方案：

```
設備 1.0 ─────────────────────────────────────────────────────
設備 2.x ─────────────────────────────────────────────────────
                              ↓
                    同一套 IPC 主程式
                              ↓
              版本差異集中於 config 設定檔
```

這讓版本差異集中於組態管理，而非程式邏輯，**減少約 75% 重複開發工作**。

### 可觀測性：log 系統重構，除錯定位提速 3x

初期設備的 log 多半留在地端 IPC。一旦需要除錯，工程師得遠端連線到設備、翻查 log——但缺乏合適的介面與分類，log 雖有記錄卻非常雜亂，定位一個問題動輒得耗上數十分鐘，複雜狀況甚至更久。

我重構了整套 log 機制：

- **分級**：將 log 區分為 `info` / `warn` / `error` / `fatal`
- **分類與事件化**：依類別與事件標記，讓 log 結構化、可查詢
- **排程上拋雲端**：log 定期上傳，工程師可直接在 SCADA 即時監測，不必再遠端登入設備翻找
- **篩選定位**：支援依等級、類別、事件、時間篩選，快速縮小範圍再分析根因

結果：除錯定位的耗時會因問題複雜度而異，但整體而言查找與定位的**效率約提升 3 倍（耗時縮短約 2/3）**。舉例來說，一個原本需約 60 分鐘的 log 查找，可縮短到 20 分鐘內。這也是讓「整合系統」真正可維護的關鍵——可觀測，才能快速止血。

### 資料備援：IPC 資料庫雲端異地備份

針對現場網路不穩定與設備端資源受限，另外設計了排程備援機制：定期將 IPC 資料庫資料備份並上傳雲端，做**異地備援（DR）**，將備援週期（RPO）控制在 **24 小時內**，確保關鍵資料在設備或現場故障時仍可回復。

### 跨公司技術協作

作為公司與設備商工程部的主要技術窗口，長期參與每週技術會議，協助：

- 釐清跨組織需求，轉化為可實作的技術規格
- 對齊架構設計與實作方向
- 降低跨公司協作中的需求理解落差

## 技術棧

**邊緣端**：Python、OPC UA（PLC通訊）、YOLOv8（AI推論）、OpenCV

**雲端整合**：REST APIs、IPFS

**可觀測性與資料**：PostgreSQL、分級 log、排程上拋雲端、SCADA 即時監測、雲端異地備援

**協作工具**：Git、多 repository 管理

## 學習與反思

這個專案最大的收穫，是讓我深刻理解「工業系統整合」的複雜性——問題往往不只是技術實作，更多時候是在：

1. **理解真實限制**：現場的網路、設備資源、操作習慣都與開發環境不同
2. **設計可演進的架構**：系統要在持續變化的需求下維持可維護性
3. **跨組織的技術溝通**：需求理解的落差，往往比技術問題更難解決
