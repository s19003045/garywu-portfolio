動態消息系統設計

整題的靈魂只有一句：把昂貴的工，從每秒 58 萬次的「讀」，搬到每秒 5.8 千次的「寫」。其餘所有元件，都是被一個具體瓶頸逼出來的。

★ 先記這個

八條核心心法

題目會忘，心法不會。這八條是換任何題都能套用的底層。

01 瓶頸驅動
沒有瓶頸就不加元件。一開口倒出所有元件＝扣分，因為面試官無法分辨你是真懂還是背清單。
02 工從讀搬到寫
讀寫頻率差數量級時，把昂貴計算挪到頻率低的一側。算一次、存起來、之後直接拿。
03 不用單一方案
99.9% 長尾走便宜的路，0.0x% 的 hot key 走特別的路。
04 挑對分流維度
選穩定、可預測、對應成本來源的指標（粉絲數），不要選會抖的（寫入耗時）。
05 無狀態擴展
壓力解開不會消失，只流到下一個最弱環節——通常是有狀態的儲存層，那才是天花板。
06 一致性定生死
同一個延遲，在「最終一致」系統是可容忍退化，在「強一致」系統是致命錯誤。
07 共享不複製
凡是被大量人重複讀的東西，抽出來存一份大家共享，絕不複製。
08 笨方法不死
早期的笨設計很少是錯的，它只是不該在熱路徑上——但幾乎永遠是你最後的保險絲。

框架 怎麼走一道題

五拍框架

01 第一拍

釐清需求

聽到模糊題目，第一件事不是畫架構，而是問範圍。判斷一個範圍問題好不好，用這把尺：

關鍵的尺

「這個問題會不會 fork 架構？」不同答案會導向不同架構的，才值得問；只影響前端呈現的（一次載幾筆、圖片解析度、回覆排序），是細節不是驅動。

這題真正會 fork 架構的三個勝負手：規模（用戶數、追蹤數、發文量）、讀寫比（決定 push 還是 pull）、一致性／延遲容忍度（新貼文要不要即時可見）。

本題定下的範圍：5 億註冊、2 億 DAU、平均追蹤 200 人、每天約 5 億則發文；讀寫比約 100:1；feed P99 < 200ms，但新貼文最終一致即可；99% 的人 < 5000 粉絲，極少數名人上千萬。

02 第二拍

估算規模

指標算式數量級
寫入 QPS5 億 ÷ 86400≈ 5,800 / s
讀取 QPS寫入 × 100≈ 580,000 / s

關鍵體感：讀取比寫入高 100 倍。這個比例是後面所有設計的轉軸。

03 第三拍

高層設計：V0 → V1 → V2

V0 · 天真拉取（naive pull）

三張正規化的表，feed 在讀取當下現場 JOIN 組出來。

-- 打開 feed 時跑的那句 SQL
SELECT p.* FROM posts p
WHERE p.user_id IN (SELECT following_id FROM follows WHERE follower_id = U)
ORDER BY p.created_at DESC
LIMIT 20;

ORDER BY … LIMIT 最致命：為了拿最新 20 筆，DB 必須先撈出 200 人最近的全部貼文、合併排序、再丟掉其餘（為了 top-K 付出全量代價）。關鍵字是時機（read time），不是地點（DB）。地點難改，時機可改。

核心翻轉 · 把工從讀搬到寫

V1 · Fan-out-on-write（寫入推播）

原則

hot path（讀取）越笨越好，把複雜度推給比較不頻繁的那一側（寫入）。

V2 · 混合推拉（hybrid push / pull）

問題只出在那 0.0x% 的名人。普通人的 push 跑得好好的，不必動——只對名人換一種相反的策略。

push vs pull 對照

Push（fan-out-on-write）Pull（fan-out-on-read）
貴的工發生在寫入時讀取時
適合普通人（粉絲少）名人（粉絲極多）
讀取成本極低（讀 inbox）高（現場撈）
寫入成本高（展開所有粉絲）極低（只寫自己）
失敗模式名人寫入爆炸讀取現場排序爆炸

04 第四拍

深挖瓶頸（收尾細節）

inbox 存哪？→ Redis Sorted Set

讀取極頻繁要快、且能從 DB 重算所以掉了不致命 → 放 Redis（記憶體），它是快取不是 source of truth。用 Sorted Set，score = 貼文建立時間戳，Redis 自動依時間排序。

收尾決策

存 id 不存內容：inbox 只放 post_id，貼文本體另存一份大家共享。否則川普一則文被複製 3000 萬份，儲存爆炸、改一字要改 3000 萬處。

inbox 長度上限 ≈ 1000：由「使用者單次合理滑動深度」決定，不是追蹤數。滑穿的人 → 退回 V0 那句查詢打 DB（冷路徑，慢但正確，幾乎不觸發）。

merge 在 App Server 記憶體：讀取當下拿兩串已排序資料、線性合併、拼完即丟、不落地。絕不把名人文寫進 inbox（那等於對名人 fan-out，繞回原點）。

寫入路徑非同步化 → Kafka

同步寫 5000 個 inbox 會卡死使用者——他不該為了一件他不關心的事（推給粉絲）乾等；而且中途失敗現在沒人補救。兩種期待定義了需求：發文者要即時回饋、粉絲要最終一定看得到。

三個一定被追的坑：

  • 承諾邊界：回「成功」的唯一前提是 posts 表 + Kafka 兩個持久化都落地。只要落地，App Server 下一毫秒爆炸也不會丟貼文。
  • 冪等性（idempotency）：worker 重試會重寫已寫過的 inbox。靠穩定的業務鍵達成冪等：member = post_id、score = 貼文的 created_at（不是寫入當下的時間）。這跟售票防「按兩次付兩次」是同一個性質。
  • 名人不進 Kafka：否則川普一發文往 queue 灌 1.1 億任務，壓垮 worker。V2 的粉絲數閾值一路貫穿到「要不要進 Kafka」。

05 第五拍

失敗與取捨

中級的人設計「一切正常時」的系統，資深的人設計「東西壞掉時還能撐住」的系統。

失敗一 · consumer lag（worker 跟不上）

  • 止血：worker 無狀態 → 水平擴展（50 → 500 個）。Kafka 的 consumer group 原生支援自動重新分配。
  • 止血的極限：壓力不消失，只從 worker 移到下一站 = 有狀態的 Redis。那才是真正天花板，要提前容量規劃。
  • 可不可接受：可容忍的暫時退化——因為系統承諾「最終一致」，延遲幾秒不違反任何承諾。同樣的 lag 發生在售票庫存就是致命故障（會超賣）。差別不在技術，在業務的一致性容忍度。

失敗二 · Redis 整個掛掉

定性：inbox 是快取（能從 posts + follows 重算）→ Redis 掛是效能災難，不是資料災難。重建來源不是 Kafka（它有保留期、存「事件」不是「狀態」），而是重跑 V0 那句查詢——笨方法第三次回來救場。

RPO（可容忍遺失多少資料）RTO（可容忍癱瘓多久）
inbox（快取）寬鬆（可重算，無資料遺失）重這個
Postgres（真相來源）必須嚴格（貼文一則不能丟）次要

失敗三 · hot key 三次現身

那個「全體粉絲共享一份」的名人快取，本身就是一個 hot key——同一個 key 永遠雜湊到同一個分片節點，分片解不了。

錯誤直覺

用 Kafka 當讀取緩衝。❌ Kafka 是給「寫入／任務」削峰的，不是給「讀取」加速的。讀取必須即時，丟進 queue＝讓讀取延遲變無限長。讀取熱點永遠往「快取／複製／推到離使用者更近」想，不是「排隊」。

正解：① 唯讀副本（replica）＋ load balancer 打散；② 本地快取（local cache）——爆紅貼文這幾分鐘內容不變，讓每台 App Server 本機記憶體快取幾秒，1 億次讀取被幾百台機器吸收掉絕大部分；③ key 加隨機後綴打散到多節點再聚合。

∑ 收束

完整架構一圖

一句話回顧 發文 → App Server 寫 posts + 看粉絲數分流。普通人 fan-out 事件進 Kafka → worker 冪等寫進每個 inbox（Sorted Set，post_id 當 member、時間戳當 score）。名人只更新自己的共享快取、不展開。讀取時 App Server 並行讀〔自己的 inbox〕＋〔追蹤名人的共享快取〕，記憶體 merge 取最新 20 筆，再用 id 補貼文內容。

✎ 給自己

個人複習提醒

已內化

會自己接話、自己算規模、自己指認 hot key，甚至會停下來質疑「我是不是在迎合名詞」。這個自我懷疑＝瓶頸驅動內化的徵兆。

待加強

回答先收束到「這一坑的核心性質是什麼」，再展開講手段。Redis 那題該先點「inbox 是 cache → 效能災難」，再講重建；冪等那題該先說「我要的是冪等性」，再講 Sorted Set。先講性質、再講手段——回答會從「會解」升級成「讓人信服你懂為什麼」。
